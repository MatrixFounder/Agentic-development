# 4. Модель данных

**Цель.** Задать поля и инварианты записи так, чтобы реплики сходились к одному состоянию после синхронизации.

## 4.1 Границы раздела

**В зоне ответственности раздела.**

- сущности `Record`, `Operation`, `LocalRecord`, `SyncState`, `ConflictEntry` и их поля
- инварианты I-1 … I-15
- правило разрешения конфликтов и его постусловия
- случай «удаление против правки» (C-1 … C-4)

**Вне зоны ответственности раздела.**

- транспорт синхронизации, коды и формат HTTP-запросов — раздел 5
- аутентификация устройства и выдача токенов — сервис identity
- миграции схемы локальной базы — раздел 6
- бинарные вложения и их выгрузка — раздел 7
- шифрование локальной базы на устройстве — раздел 8
- экран разрешения конфликтов — команда клиента
- совместное редактирование записи несколькими пользователями — вне продукта, D-5

## 4.2 Термины

**Снимок** — последний ответ сервера по записи, принятый клиентом.

**Операция** — строка локальной очереди, описывающая одно изменение одной записи.

**Пересборка** — построение новой операции поверх более свежего снимка.

**Конфликт** — состояние, при котором `op.base_version` меньше `record.version`.

## 4.3 Сущности

### 4.3.1 `Record` — запись на сервере

| Поле | Тип | Кто назначает | Правило |
| :--- | :--- | :--- | :--- |
| `record_id` | UUIDv7 | клиент-создатель | уникален в пределах `owner_id` |
| `owner_id` | string | сервер | идентификатор пользователя |
| `version` | int64 | сервер | растёт на 1 на каждую принятую операцию |
| `updated_at` | timestamp UTC | сервер | время принятия операции |
| `updated_by_device` | string | сервер | `device_id` последней принятой операции |
| `deleted` | bool | сервер | значение по умолчанию `false` |
| `deleted_at` | timestamp UTC, nullable | сервер | заполняется при `delete` |
| `payload` | object | клиент | доменные поля записи |
| `field_updated_at` | map<string, timestamp> | клиент | метка на каждый ключ `payload` |

### 4.3.2 `Operation` — элемент локальной очереди

| Поле | Тип | Кто назначает | Правило |
| :--- | :--- | :--- | :--- |
| `op_id` | UUIDv7 | клиент | ключ идемпотентности на сервере |
| `record_id` | UUIDv7 | клиент | целевая запись |
| `seq` | int64 | клиент | монотонный номер в очереди устройства |
| `type` | enum | клиент | `create`, `update`, `delete`, `restore` |
| `base_version` | int64 | клиент | `version` снимка, на котором построена операция |
| `touched` | set<string> | клиент | имена изменённых ключей `payload` |
| `patch` | object | клиент | новые значения ключей из `touched` |
| `field_updated_at` | map<string, timestamp> | клиент | локальная метка на каждый ключ из `touched` |
| `device_id` | string | клиент | идентификатор устройства-автора |
| `attempts` | int | клиент | число выполненных пересборок |
| `status` | enum | клиент | `queued`, `sent`, `accepted`, `conflict`, `manual` |

### 4.3.3 `LocalRecord` — состояние записи на устройстве

| Поле | Тип | Кто назначает | Правило |
| :--- | :--- | :--- | :--- |
| `record_id` | UUIDv7 | клиент | ключ строки |
| `server_snapshot` | object | клиент | последний принятый ответ сервера |
| `snapshot_version` | int64 | клиент | `version` снимка |
| `materialized` | object | клиент | снимок плюс очередь, только для чтения |

### 4.3.4 `SyncState` — одна строка на устройство

| Поле | Тип | Кто назначает | Правило |
| :--- | :--- | :--- | :--- |
| `device_id` | string | клиент | назначается при первом запуске, OQ-1 |
| `last_pull_cursor` | opaque string | сервер | курсор последней успешной выгрузки |
| `next_seq` | int64 | клиент | следующий свободный `seq` |
| `clock_offset_ms` | int64 | клиент | `updated_at` сервера минус локальные часы |

### 4.3.5 `ConflictEntry` — отвергнутое изменение

| Поле | Тип | Кто назначает | Правило |
| :--- | :--- | :--- | :--- |
| `conflict_id` | UUIDv7 | клиент | ключ строки |
| `record_id` | UUIDv7 | клиент | запись-источник |
| `op_id` | UUIDv7 | клиент | операция-источник |
| `reason` | enum | клиент | `field_lost`, `deleted_remotely`, `attempts_exceeded`, `record_purged` |
| `lost_fields` | map<string, any> | клиент | ключ поля и отвергнутое значение |
| `created_at` | timestamp UTC | клиент | локальное время записи строки |
| `resolved` | bool | клиент | значение по умолчанию `false` |

## 4.4 Инварианты

- **I-1** — `version` увеличивается ровно на 1 на каждую принятую операцию. Проверяет: T-1.
- **I-2** — `version` назначает только сервер. Проверяет: T-1.
- **I-3** — `record_id` уникален в пределах `owner_id`. Проверяет: уникальный индекс базы.
- **I-4** — операции одного `record_id` уходят на сервер по возрастанию `seq`. Проверяет: T-11.
- **I-5** — операция покидает очередь после статуса `accepted` или после записи `ConflictEntry`. Проверяет: T-12.
- **I-6** — `materialized` детерминированно вычисляется из снимка и очереди. Проверяет: T-10.
- **I-7** — повторная отправка того же `op_id` не создаёт вторую версию. Проверяет: T-13.
- **I-8** — при `deleted = true` операция `update` не изменяет `payload`. Проверяет: T-6.
- **I-9** — значение `deleted = false` устанавливает только операция `restore`. Проверяет: T-8.
- **I-10** — `field_updated_at` содержит ключ на каждый ключ `payload`. Проверяет: валидация схемы на приёме.
- **I-11** — часы устройства не влияют на `version` и на `updated_at`. Проверяет: T-14.
- **I-12** — отвергнутое значение поля сохраняется в `ConflictEntry`. Проверяет: T-4, T-6.
- **I-13** — сервер хранит запись с `deleted = true` не меньше `retention_deleted`. Проверяет: T-9.
- **I-14** — операция `delete` не изменяет `payload` и `field_updated_at`. Проверяет: T-8.
- **I-15** — клиент не создаёт запись заново после ответа `410`. Проверяет: T-9.

**Why (I-14).** `restore` возвращает значения полей из сохранённого `payload`.

**Why (I-15).** Пересоздание вернуло бы данные, удалённые пользователем на другом устройстве.

## 4.5 Правило разрешения конфликтов

Ключ сравнения поля `f` — пара `(field_updated_at[f], device_id)`. Сравнение лексикографическое.

**Why.** Пара задаёт полный порядок, поэтому результат не зависит от порядка прихода устройств.

Процедура:

1. Сервер сравнивает `op.base_version` с `record.version`. Постусловие: выбран шаг 2 или шаг 3.
2. При равенстве сервер применяет `patch` и увеличивает `version` на 1. Постусловие: `record.version = op.base_version + 1`.
3. При различии сервер возвращает `409` и текущую запись. Постусловие: запись на сервере не изменена.
4. Клиент сохраняет ответ как новый снимок. Постусловие: `snapshot_version = record.version`.
5. Клиент сравнивает ключи полей из `op.touched`. Постусловие: `touched` разделён на `win` и `lose`.
6. Клиент строит операцию из полей `win` с `base_version = snapshot_version`. Постусловие: `attempts` увеличен на 1.
7. Клиент пишет поля `lose` в `ConflictEntry` с `reason = field_lost`. Постусловие: отвергнутые значения сохранены.
8. При пустом `win` клиент ставит `status = accepted` без отправки. Постусловие: очередь короче на одну операцию.
9. Клиент отправляет новую операцию и переходит к шагу 1. Постусловие: счётчик `attempts` не превышает `max_rebase_attempts`.
10. При `attempts = max_rebase_attempts` клиент ставит `status = manual` и `reason = attempts_exceeded`. Постусловие: операция не отправляется до действия пользователя.

Производные числа:

- `max_rebase_attempts = 5 = N_devices + 1`, где `N_devices = 4` — потолок числа устройств на аккаунт (OQ-5); применено 5.
- `retention_deleted = 90 дней = P95(офлайн-период) + 30`; измерено `P95 = 60` и не подтверждено (OQ-3); применено 90. Значение 90 — потолок хранения.

## 4.6 Удаление против правки

| Случай | Вход | Состояние на сервере | Состояние на клиенте |
| :--- | :--- | :--- | :--- |
| C-1 | `delete` принят, затем `update` с устаревшей `base_version` | `deleted = true`, `version` не меняется | `ConflictEntry`, `reason = deleted_remotely` |
| C-2 | `update` принят, затем `delete` с устаревшей `base_version` | `deleted = true`, `version + 1`, `payload` сохранён | снимок обновлён, `ConflictEntry` не создаётся |
| C-3 | `update` для записи, вычищенной по `retention_deleted` | ответ `410`, запись отсутствует | `ConflictEntry`, `reason = record_purged` |
| C-4 | `restore` от пользователя | `deleted = false`, `version + 1`, `payload` восстановлен | снимок обновлён |

Правило C-2: сервер применяет `delete` независимо от `op.base_version`.

**Why.** `payload` живёт до истечения `retention_deleted`, поэтому `restore` возвращает данные правки.

## 4.7 Режимы отказа

- **R-1** — часы устройства отстают на величину больше интервала правок → поле проигрывает сравнение и попадает в `ConflictEntry`. Обнаруживает: T-14 и метрика `conflict_lost_fields`.
- **R-2** — очередь отправлена не по возрастанию `seq` → вторая операция получает `409` при неизменной записи. Обнаруживает: T-11.
- **R-3** — устройство вышло в сеть позже `retention_deleted` → сервер отвечает `410` на весь пакет операций. Обнаруживает: T-9.
- **R-4** — `field_updated_at` не содержит ключа изменённого поля → сервер отклоняет операцию на валидации схемы. Обнаруживает: T-15.

## 4.8 Обязательства по тестам

- **T-1** — `base_version = record.version` → ответ `200`, `version` увеличен на 1;
  ломается при мутации: инкремент заменён на присваивание.
- **T-2** — `base_version < record.version` → ответ `409`, `record.version` не изменён;
  ломается при мутации: сравнение версий снято.
- **T-3** — две операции разных устройств по разным полям → оба значения видны в снимке;
  ломается при мутации: `patch` заменяет `payload` целиком.
- **T-4** — две операции по одному полю с разными метками → побеждает большая `field_updated_at`;
  ломается при мутации: сравнение меток инвертировано.
- **T-5** — две операции по одному полю с равными метками → побеждает больший `device_id`;
  ломается при мутации: тай-брейк по `device_id` удалён.
- **T-6** — `update` с `base_version` до `delete` → `deleted = true`, создан `ConflictEntry`;
  ломается при мутации: `update` снимает флаг `deleted`.
- **T-7** — тот же вход, что в T-5, поданный в обратном порядке → тот же итоговый `payload`;
  ломается при мутации: тай-брейк по `device_id` заменён на порядок прихода.
- **T-8** — `restore` после `delete` → `deleted = false`, `payload` равен значению до удаления;
  ломается при мутации: `delete` очищает `payload`.
- **T-9** — `update` для вычищенной записи → ответ `410`, новая запись не создана;
  ломается при мутации: сервер создаёт запись по `record_id` из операции.
- **T-10** — один снимок и одна очередь, пересчёт дважды → одинаковый `materialized`;
  ломается при мутации: порядок применения очереди взят из хеш-таблицы.
- **T-11** — очередь из двух операций одной записи → отправка по возрастанию `seq`;
  ломается при мутации: отправка выполняется конкурентно.
- **T-12** — ответ `409` на операцию → операция остаётся в очереди до записи `ConflictEntry`;
  ломается при мутации: операция удаляется по любому ответу сервера.
- **T-13** — повтор операции с тем же `op_id` → `version` не изменился;
  ломается при мутации: ключ идемпотентности не проверяется.
- **T-14** — операция с меткой из будущего на 1 час → `updated_at` взят у сервера;
  ломается при мутации: сервер копирует клиентскую метку в `updated_at`.
- **T-15** — операция без ключа в `field_updated_at` → ответ `422`, запись не изменена;
  ломается при мутации: проверка полноты карты меток снята.

## 4.9 Решения

- **D-1, 2026-08-05, архитектор сервера**: версия записи — целочисленный счётчик сервера. Отклонено: векторные часы — размер вектора растёт линейно по числу устройств аккаунта.
- **D-2, 2026-08-05, архитектор сервера**: `delete` применяется независимо от `base_version`. Отклонено: `update` снимает флаг `deleted` — каждое устройство с устаревшей очередью возвращает запись повторно.
- **D-3, 2026-08-05, архитектор клиента**: пересборку операции выполняет клиент-инициатор. Отклонено: слияние на сервере — сервер тогда знает схему `payload` каждого типа записи.
- **D-4, 2026-08-05, архитектор клиента**: разрешение конфликта идёт по полям. Отклонено: last-writer-wins по записи целиком — правка одного поля стирает остальные поля второго устройства.
- **D-5, 2026-08-05, продукт**: запись принадлежит одному `owner_id`. Отклонено: общий доступ к записи — модель тогда хранит права доступа и вторую ось конфликтов.

## 4.10 Открытые вопросы

- **OQ-1** — Сохраняется ли `device_id` после переустановки приложения? Блокирует: тай-брейк в 4.5 и нумерацию `seq`. Владелец: клиентская команда.
- **OQ-2** — Что происходит при `restore` и `delete`, построенных на одном снимке? Блокирует: T-8. Владелец: архитектор сервера.
- **OQ-3** — Подтверждён ли `P95` офлайн-периода на уровне 60 дней? Блокирует: `retention_deleted`. Владелец: аналитика.
- **OQ-4** — Применяется ли правило 4.5 к полям типа «массив» поэлементно? Блокирует: T-4. Владелец: архитектор клиента.
- **OQ-5** — Ограничено ли число устройств на аккаунт значением 4? Блокирует: `max_rebase_attempts`. Владелец: продукт.
