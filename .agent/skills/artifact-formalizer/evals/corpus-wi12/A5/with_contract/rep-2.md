## 4. Модель данных и инварианты

### 4.1 Границы раздела

**В зоне ответственности раздела.**

- сущности сервера и клиента, их поля и типы
- инварианты, проверяемые на любом снимке состояния
- правило разрешения конфликтов записи
- случай «удаление против правки»
- тестовые обязательства к перечисленному

**Вне зоны ответственности раздела.**

- транспорт, формат RPC и пагинация выборки изменений — раздел 6
- аутентификация устройства и выдача токенов — раздел 3
- политика повторов и backoff при ошибке сети — раздел 6.4
- шифрование локального хранилища — раздел 8
- миграции схемы поля `body` — раздел 9
- вложения и бинарные объекты — раздел 10
- экраны разрешения конфликтов и показа черновиков — документ `UX-SYNC-2`
- совместное редактирование записи разными пользователями — не поддерживается, требование R-3
- полнотекстовый индекс над `body` — раздел 11

### 4.2 Термины

`Tombstone` — версия записи, у которой `is_deleted = true` и `body = null`.

`Effective time` — момент правки, использованный при сравнении: `client_time` внутри окна доверия, иначе `server_time`.

`Окно доверия` — интервал `|client_time − server_time| ≤ 300 с`.

`Конфликт поля` — состояние, при котором `field_version[f] > op.base_version`.

### 4.5 Инварианты

| ID | Утверждение | Обнаруживается |
| :--- | :--- | :--- |
| INV-1 | `Record.version` растёт ровно на 1 на каждое принятое изменение | SYNC-01 |
| INV-2 | При `Record.is_deleted = true` поле `body` равно `null` | SYNC-02 |
| INV-3 | Переход `is_deleted` из `true` в `false` отсутствует | SYNC-03 |
| INV-4 | `LocalRecord.base_version ≤ Record.version` для того же `record_id` | SYNC-04 |
| INV-5 | Для одного `record_id` не более одной операции в статусе `sent` | SYNC-05 |
| INV-6 | Операции одной записи отправляются по возрастанию `seq` | SYNC-06 |
| INV-7 | Повторная доставка `op_id` не меняет состояние сервера | SYNC-07 |
| INV-8 | `sync_state = dirty` ⟺ есть операция записи в статусе `queued` или `sent` | SYNC-08 |
| INV-9 | Операция покидает очередь только в статусе `acked` или `rejected` | SYNC-09 |
| INV-10 | `field_version[f] ≤ Record.version` для каждого ключа `f` | SYNC-10 |
| INV-11 | `Device.sync_cursor` не убывает | SYNC-11 |
| INV-12 | Tombstone и его `body_snapshot` хранятся не менее `T_tomb` | SYNC-12 |
| INV-13 | Две реплики одного префикса `ChangeLog` дают одинаковый `body` | SYNC-13 |

#### Пояснения к отдельным инвариантам

**INV-5, INV-6.**

**Why.** Патчи одной записи не коммутативны ⇒ параллельная отправка двух операций даёт разный результат при разном порядке приёма.

**INV-7.**

**Why.** Клиент повторяет операцию после разрыва соединения ⇒ без дедупликации по `op_id` версия растёт дважды.

**INV-9.**

**Why.** Очередь — единственная копия непринятых правок ⇒ удаление до ответа сервера теряет правку без следа.

**INV-12.**

`T_tomb = 90 суток = 3 × 30 суток`; measured: 30 суток — предельный офлайн-период устройства из требования R-12; applied: 90 суток — нижняя граница хранения, потолок не задан.

### 4.6 Правило разрешения конфликтов

Сервер обрабатывает операцию `op` в следующем порядке.

1. Найти строку `AppliedOp` по `op.op_id`. Постусловие: при попадании возвращён сохранённый результат, шаги 2–8 пропущены.
2. Загрузить `Record` по `op.record_id`. Постусловие: известны `version`, `is_deleted`, `field_version`, `field_time`.
3. Сравнить `op.base_version` с `Record.version`. Постусловие: при `op.base_version > Record.version` операция отклонена с кодом `invalid_base`.
4. Проверить `Record.is_deleted`. Постусловие: при `true` и `op.kind ≠ delete` операция отклонена с кодом `record_deleted`.
5. Вычислить effective time операции. Постусловие: `t_op = op.client_time` внутри окна доверия, иначе `t_op = server_time`.
6. Для каждого поля `f` из `op.patch` при `field_version[f] ≤ op.base_version`: записать значение. Постусловие: `field_version[f] = version + 1`, `field_time[f] = t_op`.
7. Для каждого конфликтного поля `f`: записать значение при `t_op > field_time[f]`. Постусловие: при равенстве `t_op` и `field_time[f]` выигрывает больший `device_id` в лексикографическом порядке.
8. Зафиксировать результат. Постусловие: `version` увеличена на 1, добавлена строка `ChangeLog`, добавлена строка `AppliedOp`.

Слияние применяется к полям верхнего уровня `body`. Вложенный объект заменяется целиком.

Ответ на `applied` содержит `resulting_version` и каноническое `body`. Клиент присваивает `LocalRecord.body` каноническое тело и `base_version = resulting_version`.

Клиент, получивший `invalid_base`, запрашивает запись целиком и пересоздаёт операцию от новой `base_version`.

**Why.** Клиентские часы не проверяются сервером ⇒ окно доверия ограничивает влияние сдвига часов 300 секундами.

### 4.7 Удаление против правки

Случай описан отдельно, потому что операции `delete` и `update` не сливаются по полям.

| Случай | Порядок приёма сервером | Результат на сервере | Результат на клиенте-авторе правки |
| :--- | :--- | :--- | :--- |
| C-1 | `delete`, затем `update` | `update` отклонён кодом `record_deleted` | `LocalRecord` удалён, создан `RecoveredDraft` с `reason = record_deleted` |
| C-2 | `update`, затем `delete` | `delete` применён, `body_snapshot` содержит принятую правку | при pull создан `RecoveredDraft` с `reason = overwritten_by_delete` |
| C-3 | `delete`, затем `delete` | вторая операция подтверждена без роста `version` | `LocalRecord` удалён, черновик не создан |
| C-4 | `delete` при `delete.base_version < Record.version` | `delete` применён | правки, принятые после `base_version`, попадают в `body_snapshot` |

Правила случая:

1. Операция `delete` применяется при `is_deleted = false` и `delete.base_version ≤ Record.version`. Постусловие: `is_deleted = true`, `body = null`, `deleted_at = server_time`, `version` увеличена на 1.
2. Строка `ChangeLog` для `delete` содержит `body_snapshot` последней версии тела. Постусловие: тело доступно для восстановления в течение `T_tomb`.
3. Операция `update` над tombstone отклоняется кодом `record_deleted`. Постусловие: клиент создаёт `RecoveredDraft` из `op.patch` и удаляет `LocalRecord`.
4. Клиент при pull изменения `kind = delete` сравнивает `ChangeLog.body_snapshot.last_writer_device` со своим `device_id`. Постусловие: при совпадении создан `RecoveredDraft` с `reason = overwritten_by_delete`.
5. Повторное удаление подтверждается без роста `version` и без строки `ChangeLog`.
6. Клиент не переиспользует `record_id` удалённой записи для новой записи.

**Why.** Удаление необратимо по INV-3 ⇒ повторное использование идентификатора даёт запись, которую сервер сразу отклоняет.

**Why.** Удаление доминирует над правкой ⇒ единственный носитель потерянного текста — `body_snapshot` и локальный `RecoveredDraft`.

### 4.8 Риски

| ID | Severity | Риск |
| :--- | :--- | :--- |
| R-1 | Critical | Сдвиг часов устройства внутри окна доверия → выигрывает более старая правка |
| R-2 | Major | Очередь удаляет операцию до ответа сервера → правка исчезает без следа |
| R-3 | Major | Срок хранения tombstone истёк раньше возврата устройства в сеть → повтор удалённой записи |
| R-4 | Minor | Число `RecoveredDraft` растёт без ограничения → расход дискового пространства устройства |

R-1 обнаруживается тестом SYNC-14. R-2 обнаруживается тестом SYNC-09. R-3 обнаруживается тестом SYNC-12. R-4 обнаруживается метрикой `drafts_per_device` из раздела 12.

### 4.9 Тестовые обязательства

- `SYNC-01` — две операции подряд к одной записи → `version` равна 3; fails when инкремент заменён на присвоение `client_time`.
- `SYNC-02` — `delete` по записи с непустым `body` → `body` равно `null`; fails when очистка `body` удалена.
- `SYNC-05` — две операции одной записи в очереди → сервер получил вторую после ответа на первую; fails when ограничение параллелизма снято.
- `SYNC-07` — повтор одного `op_id` → `version` не изменилась; fails when таблица `AppliedOp` не читается на шаге 1.
- `SYNC-12` — pull через `T_tomb − 1 сутки` после удаления → изменение `kind = delete` присутствует; fails when срок хранения уменьшен.
- `SYNC-13` — два клиента применяют один префикс `ChangeLog` → тела записей совпадают; fails when правило шага 7 использует `server_time` вместо `t_op`.
- `SYNC-14` — операция с `client_time` на 1 час впереди → применён `server_time`; fails when окно доверия расширено.

### 4.10 Решения

`D-1`, 2026-08-05, архитектор синхронизации: слияние выполняется по полям верхнего уровня. Rejected: слияние по всей записи — теряет правку второго поля в 100% случаев параллельной правки разных полей.

`D-2`, 2026-08-05, архитектор синхронизации: удаление доминирует над правкой. Rejected: правка воскрешает запись — нарушает INV-3 и делает `version` неупорядоченной по `is_deleted`.

`D-3`, 2026-08-05, серверная команда: `client_time` вне окна доверия заменяется на `server_time`. Rejected: доверие часам устройства без проверки — сдвиг часов на сутки закрепляет проигравшую правку навсегда.
