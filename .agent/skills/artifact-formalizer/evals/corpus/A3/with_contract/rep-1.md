# TASK — Ключи идемпотентности в обработчике вебхуков платёжного провайдера

## Цель

Применять каждое событие провайдера ровно один раз, так что повторная доставка не изменяет состояние платежа.

## Термины

- **Идентификатор события** — значение, которое провайдер передаёт в теле вебхука для одной доставки.
- **Ключ идемпотентности** — запись хранилища, которая построена из имени провайдера и идентификатора события.
- **Применение события** — операция обработчика, которая изменяет состояние платежа или связанных сущностей.
- **Окно повторных доставок** — интервал, в течение которого провайдер повторяет доставку одного события.

Значения severity в этом документе: `blocker`, `major`, `minor`.

## Допущения

| id | Допущение | Проверяется |
| :--- | :--- | :--- |
| A-1 | Провайдер передаёт идентификатор события в теле каждой доставки | документация провайдера |
| A-2 | Провайдер повторяет доставку с тем же идентификатором | документация провайдера |
| A-3 | Проект использует СУБД с поддержкой уникальных ограничений | схема проекта |

Допущение, которое не подтвердилось, поднимается как Open Question до начала шага S-1.

## Входные данные

| Источник | Что даёт |
| :--- | :--- |
| HTTP-запрос вебхука | тело события: идентификатор, тип, полезная нагрузка |
| Документация провайдера | имя поля идентификатора, окно повторных доставок |
| Текущий обработчик вебхуков | точка, в которой событие применяется к состоянию платежа |
| Схема БД проекта | место для таблицы ключей и уникального индекса |
| Конфигурация приложения | место для параметра срока хранения ключей |

## Область

In scope: чтение идентификатора события, хранение ключей, однократное применение, удаление просроченных ключей, тесты T-1…T-9.

Out of scope: проверка подписи вебхука (задача по безопасности транспорта), повторы исходящих запросов к провайдеру (задача клиента API), обратное применение к событиям, доставленным до этой задачи (отдельная задача миграции).

## Требования

- **R-1** — Обработчик читает идентификатор события из тела запроса.
- **R-2** — Обработчик применяет событие с данным идентификатором не более одного раза.
- **R-3** — Хранилище объявляет уникальное ограничение на пару `(provider, event_id)`.
- **R-4** — Ключ идемпотентности хранит `provider`, `event_id`, время первой записи, статус применения.
- **R-5** — Обработчик не должен применять событие до подтверждённой хранилищем записи ключа.
  Нарушение видно на входе: две одновременные доставки одного `event_id`.
- **R-6** — Повторная доставка известного события возвращает 2xx и не изменяет состояние платежа.
- **R-7** — Запрос без идентификатора события возвращает 400 и не изменяет состояние платежа.
- **R-8** — Срок хранения ключей читается из конфигурации; литерал в коде обработчика отсутствует.
- **R-9** — Срок хранения ключей не меньше окна повторных доставок провайдера.
- **R-10** — Повторная доставка записывается в лог с уровнем `info` и полем `event_id`.

**Why (R-3).** Проверка «сначала SELECT, затем INSERT» допускает两 параллельных прохода ⇒ однократность обеспечивает только ограничение уровня хранилища.

**Why (R-7).** Идентификатор события — единственный вход механизма ⇒ его отсутствие делает однократность непроверяемой.

**Why (R-9).** Удалённый ключ неотличим от нового события ⇒ повтор внутри окна применяется второй раз.

## Шаги реализации

1. Добавить миграцию таблицы `webhook_idempotency_keys` с колонками из R-4.
   Постусловие: миграция применяется и откатывается на чистой базе.
2. Добавить уникальный индекс по `(provider, event_id)`.
   Постусловие: вторая вставка того же значения возвращает ошибку уникальности.
3. Извлечь идентификатор события в обработчике, до применения события.
   Постусловие: запрос без поля возвращает 400 (T-8).
4. Разместить запись ключа перед применением события.
   Постусловие: сценарий T-4 оставляет ровно одно применение.
5. Зафиксировать поведение при двух одновременных доставках (OQ-2).
   Постусловие: решение OD-2 записано в разделе «Решения», тест T-5 проходит.
6. Зафиксировать срок хранения и добавить параметр конфигурации (OQ-1).
   Постусловие: решение OD-1 записано, значение читается из конфигурации (T-7).
7. Добавить операцию удаления просроченных ключей вне пути обработчика.
   Постусловие: удаление не трогает ключи моложе срока хранения (T-7).
8. Добавить лог повторной доставки по R-10.
   Постусловие: сценарий T-2 оставляет одну запись `info` с `event_id`.
9. Прогнать T-1…T-9 на чистой базе.
   Постусловие: все девять проходят, ни один не пропущен.

## Открытые вопросы

- **OQ-1** — Каков срок хранения ключа идемпотентности? Blocks: шаги S-6, S-7; тест T-7. Owner: исполнитель задачи.
- **OQ-2** — Что делает обработчик, когда две доставки одного события обрабатываются одновременно? Blocks: шаг S-5; тест T-5. Owner: исполнитель задачи.

Любой ответ на OQ-2 удовлетворяет R-2 и R-5. Тест T-5 проверяет однократность, а не выбранную стратегию.

Любой ответ на OQ-1 удовлетворяет R-9.

## Решения (заполняет исполнитель до сдачи)

Форма записи:

`OD-<n>, <дата>, <исполнитель>: <что решено>. Отклонено: <альтернатива> — <измеримая причина>.`

- **OD-1** — срок хранения ключей. Значение записывается как `<значение> = <вывод>; измерено <m>; применено <a>`, с указанием, какое из двух является потолком.
- **OD-2** — поведение при одновременных доставках. Запись называет, что видит вторая доставка: ответ, статус, состояние платежа.

## Риски

| id | Условие → наблюдаемый исход | Обнаруживается | Severity |
| :--- | :--- | :--- | :--- |
| RISK-1 | запись ключа после применения → сбой между шагами даёт второе применение | T-4 | `blocker` |
| RISK-2 | уникальный индекс отсутствует → параллельные доставки дают два применения | T-5 | `blocker` |
| RISK-3 | срок хранения меньше окна повторов → удалённый ключ допускает второе применение | T-7 | `major` |
| RISK-4 | ключ без имени провайдера → совпадение идентификаторов теряет событие | T-6 | `major` |
| RISK-5 | ответ 5xx на повтор известного события → провайдер продолжает повторять доставку | T-2 | `minor` |

## Обязательства по тестам

- **T-1** — доставка с новым `event_id` → состояние платежа изменено, ключ записан; падает при удалении вставки ключа.
- **T-2** — повтор того же тела запроса → состояние платежа не изменено, ответ 2xx; падает при снятии уникального ограничения.
- **T-3** — две доставки с разными `event_id` → применены оба события; падает, если ключ строится из типа события.
- **T-4** — сбой применения после записи ключа, затем повтор доставки → ровно одно применение; падает при переносе записи ключа после применения.
- **T-5** — две одновременные доставки одного `event_id` → ровно одно применение; падает при снятии уникального индекса.
- **T-6** — одинаковый `event_id` от двух разных провайдеров → применены оба события; падает при исключении `provider` из ключа.
- **T-7** — ключ моложе окна повторных доставок → операция очистки его сохраняет; падает при сроке хранения ниже окна.
- **T-8** — запрос без идентификатора события → ответ 400, состояние платежа не изменено; падает при возврате 2xx.
- **T-9** — раздел «Решения» содержит заполненные OD-1 и OD-2.
