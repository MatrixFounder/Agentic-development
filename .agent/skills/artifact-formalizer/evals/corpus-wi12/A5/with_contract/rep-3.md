## Модель данных и инварианты

### 1. Термины

- **Операция** — элемент очереди клиента, описывающий одно изменение одной записи.
- **Патч** — набор пар «имя поля → значение» внутри операции.
- **Маркер удаления** — состояние `Record`, в котором `deleted_at` заполнено.
- **LWW** — правило выбора значения поля по наибольшей паре `(client_updated_at, device_id)`.
- **Перебазирование** — пересборка операции клиента поверх нового `base_version`.

### 2. Сущности

#### 2.1 `Record` — серверное состояние записи

| Поле | Тип | Значение |
| :--- | :--- | :--- |
| `record_id` | UUIDv7 | первичный ключ; назначает создающее устройство |
| `owner_id` | UUID | владелец записи |
| `body` | JSON-объект | прикладные поля; схема вне этого раздела |
| `version` | uint64 | номер последней применённой операции |
| `updated_at` | timestamp UTC | серверное время последней применённой операции |
| `origin_device_id` | UUID | устройство последней применённой операции |
| `deleted_at` | timestamp UTC либо `null` | `null` — запись не удалена |
| `deleted_by_device` | UUID либо `null` | заполняется вместе с `deleted_at` |

#### 2.2 `RecordChange` — журнал применённых операций

| Поле | Тип | Значение |
| :--- | :--- | :--- |
| `record_id` | UUID | ссылка на `Record` |
| `version` | uint64 | версия, созданная этой строкой |
| `op_id` | UUID | идентификатор операции клиента |
| `kind` | `upsert` либо `delete` | вид операции |
| `changed_fields` | массив строк | имена полей, изменённых этой операцией |
| `client_updated_at` | timestamp UTC | время правки по часам устройства |
| `device_id` | UUID | устройство-автор |
| `applied_at` | timestamp UTC | серверное время применения |

Первичный ключ — пара (`record_id`, `version`). Поле `op_id` уникально в пределах таблицы.

#### 2.3 `LocalRecord` — клиентская реплика записи

| Поле | Тип | Значение |
| :--- | :--- | :--- |
| `record_id` | UUID | первичный ключ |
| `base_version` | uint64 | версия последнего снимка, полученного с сервера |
| `body_synced` | JSON-объект | снимок сервера версии `base_version` |
| `body_local` | JSON-объект | состояние, отображаемое пользователю |
| `deleted_synced` | bool | маркер удаления присутствует на сервере |
| `deleted_local` | bool | удаление запрошено на этом устройстве |
| `sync_status` | `clean`, `dirty` либо `conflict` | вычисляется из очереди операций |

#### 2.4 `Operation` — элемент очереди клиента

| Поле | Тип | Значение |
| :--- | :--- | :--- |
| `op_id` | UUID | первичный ключ; генерируется один раз при создании |
| `seq` | uint64 | порядковый номер в пределах `device_id` |
| `record_id` | UUID | цель операции |
| `kind` | `upsert` либо `delete` | вид операции |
| `patch` | JSON-объект | изменённые поля; пустой для `kind = delete` |
| `base_version` | uint64 | значение `LocalRecord.base_version` на момент создания |
| `client_updated_at` | timestamp UTC | часы устройства на момент правки |
| `device_id` | UUID | устройство-автор |
| `status` | `pending`, `sending`, `applied`, `dropped` либо `failed` | состояние в очереди |
| `attempts` | uint16 | число выполненных отправок |
| `created_at` | timestamp UTC | часы устройства на момент создания |

#### 2.5 `SyncCursor` — позиция синхронизации устройства

| Поле | Тип | Значение |
| :--- | :--- | :--- |
| `user_id` | UUID | владелец данных |
| `device_id` | UUID | устройство |
| `server_cursor` | непрозрачная строка | позиция в потоке изменений сервера |
| `last_sync_at` | timestamp UTC | серверное время последнего успешного обмена |

### 3. Инварианты

#### 3.1 Серверные

- **INV-S1** — `Record.version` увеличивается ровно на 1 при каждой применённой операции. Проверка: `T-4`.
- **INV-S2** — `RecordChange` содержит строку для каждой версии от 1 до `Record.version`. Проверка: ограничение целостности при вставке.
- **INV-S3** — `deleted_at` и `deleted_by_device` заполнены оба либо пусты оба. Проверка: `CHECK` в схеме БД.
- **INV-S4** — сервер не применяет операцию `kind = upsert` к записи с заполненным `deleted_at`. Проверка: `T-3`.
- **INV-S5** — `body` сохраняется после удаления до истечения TTL маркера. Изменение этого правила заблокировано `OQ-4`.
- **INV-S6** — повторная доставка операции с известным `op_id` не меняет `version`. Проверка: `T-4`.
- **INV-S7** — `applied_at` не убывает в пределах одного `record_id`. Проверка: ограничение при вставке.
- **INV-S8** — сервер отклоняет операцию, у которой `client_updated_at` больше `applied_at` на величину допуска часов. Проверка: `T-5`.

#### 3.2 Клиентские

- **INV-C1** — `Operation.seq` строго возрастает в пределах `device_id`. Проверка: уникальный индекс по (`device_id`, `seq`).
- **INV-C2** — клиент отправляет операции одного `record_id` по возрастанию `seq`. Следующая операция отправляется после ответа на предыдущую.
- **INV-C3** — `body_local` отличается от `body_synced` только полями, перечисленными в операциях со статусом `pending`, `sending` или `failed`. Проверка: `T-6`.
- **INV-C4** — пустая очередь по записи означает равенство `body_local` и `body_synced`. Проверка: `T-6`.
- **INV-C5** — `deleted_local` равно `true` при наличии операции `kind = delete` в очереди либо при `deleted_synced = true`.
- **INV-C6** — `client_updated_at` не убывает в пределах `device_id`. При отставании часов клиент берёт значение предыдущей операции.
- **INV-C7** — `SyncCursor.server_cursor` меняется только на значение, полученное в ответе сервера.
- **INV-C8** — клиент не создаёт новую запись с `record_id`, для которого получен маркер удаления. Новая запись получает новый `record_id`.
- **INV-C9** — очередь и `LocalRecord` записываются одной транзакцией локальной БД.

**Why (INV-C9).** Перезапуск процесса между двумя записями оставил бы правку без операции ⇒ изменение не дошло бы до сервера.

### 4. Правило разрешения конфликтов

#### 4.1 Приём операции сервером

1. Найти `Record` по `record_id`. Постусловие: запись найдена либо создана с `version = 0`.
2. Проверить `op_id` в `RecordChange`. Постусловие: при совпадении ответ содержит текущую `version`, состояние не меняется.
3. Проверить допуск часов по `INV-S8`. Постусловие: при нарушении ответ `422`, `version` не меняется.
4. При заполненном `deleted_at` и `kind = upsert` перейти к §5. Постусловие: `version` не меняется.
5. При `base_version = version` применить `patch` и увеличить `version` на 1. Постусловие: строка `RecordChange` создана.
6. При `base_version < version` прочитать строки `RecordChange` для версий из интервала (`base_version`, `version`]. Постусловие: получено множество `S` изменённых полей.
7. При отсутствии строки для версии `base_version + 1` вернуть `409 rebase_required`. Постусловие: `version` не меняется.
8. Применить поля `patch`, отсутствующие в `S`. Постусловие: эти поля равны значениям из `patch`.
9. Для полей пересечения `patch` и `S` выбрать значение по правилу LWW. Постусловие: победитель определён парой (`client_updated_at`, `device_id`).
10. Увеличить `version` на 1 и записать `RecordChange` с фактически изменёнными полями. Постусловие: `version` строго больше прежней.

Сравнение пар лексикографическое. Первым сравнивается `client_updated_at`, вторым — `device_id` как строка.

**Why (шаг 9).** Пара уникальна для двух устройств одного пользователя ⇒ оба сервера-реплики получают одинакового победителя.

#### 4.2 Перебазирование на клиенте

1. Получить снимок записи и её `version` с сервера. Постусловие: `body_synced` и `base_version` обновлены.
2. Пересчитать `patch` операции от нового `base_version`. Постусловие: `patch` содержит поля, значения которых в `body_local` отличаются от `body_synced`.
3. Отбросить операцию при пустом `patch`. Постусловие: статус операции — `applied`.
4. Отправить операцию заново с прежним `op_id`. Постусловие: `attempts` увеличен на 1.

Клиент сохраняет `op_id` при перебазировании. Идемпотентность по `op_id` описана в `INV-S6`.

### 5. Удаление на одном устройстве и правка на другом

**D-3, 2026-08-05, владелец: архитектор мобильного клиента:** удаление побеждает правку. Rejected: восстановление записи правкой — операция должна нести весь `body`, поэтому размер очереди растёт с размером записи вместо размера патча.

Правила случая:

- Сервер отвечает `409 record_deleted` и возвращает `deleted_at` и `deleted_by_device`.
- Сервер не проверяет `base_version` для операций `kind = delete`. Удаление применяется при любом значении.
- Клиент переводит отклонённую операцию в статус `dropped` и сохраняет её `patch`.
- Клиент устанавливает `deleted_synced = true` и `deleted_local = true` для записи.
- Клиент удаляет строки в статусе `dropped` по истечении их срока хранения.
- Повторное создание записи выполняется по `INV-C8` — с новым `record_id`.

Обратный порядок доставки даёт то же состояние. Правка применяется, затем `delete` увеличивает `version` и заполняет `deleted_at`.

Отображение отброшенной правки пользователю в этом разделе не описано. Вопрос открыт как `OQ-1`.

### 6. Числовые параметры

- Допуск часов = 5 мин; measured: не измерено, `OQ-2`; applied: 5 мин — потолок отклонения `client_updated_at` вперёд.
- TTL маркера удаления = 90 дней = 3 × 30 дней; measured: не измерено, `OQ-3`; applied: 90 дней — потолок.
- Срок хранения `RecordChange` = TTL маркера удаления; measured: не измерено, `OQ-3`; applied: 90 дней — потолок.
- Срок хранения операций в статусе `dropped` = 30 дней; measured: не измерено, `OQ-1`; applied: 30 дней — потолок.

Срок хранения `RecordChange` равен TTL маркера удаления по шагу 7 §4.1.

### 7. Риски

- **R-1** — часы устройства отстают больше допуска часов → правка проигрывает по LWW и не попадает в `body` (обнаруживается `T-5` и метрикой расхождения часов в ответе сервера).
- **R-2** — устройство возвращается в сеть позже TTL маркера удаления → операция получает `409 rebase_required` без доступного журнала и записывает удалённые данные заново (обнаруживается `T-7`).
- **R-3** — две операции одного устройства по одной записи отправляются параллельно → порядок применения не совпадает с порядком `seq` (обнаруживается `T-8`).
- **R-4** — прикладной код меняет `body_local` без создания операции → `INV-C3` нарушен, изменение не покидает устройство (обнаруживается `T-6`).
- **R-5** — два устройства создают записи с одинаковым `record_id` → вторая операция интерпретируется как правка первой (обнаруживается `T-9`).

### 8. Обязательства по тестам

- **T-1** — операции A и B меняют разные поля из одного `base_version` → `body` содержит оба изменения.
  - fails when: слияние по полям заменено на замену всего `body`.
- **T-2** — операции A и B меняют одно поле из одного `base_version` → значение равно значению с наибольшей парой (`client_updated_at`, `device_id`).
  - fails when: из правила сравнения убран `device_id`.
- **T-3** — `delete` от устройства A, затем `upsert` от устройства B → `deleted_at` заполнено, ответ B содержит `409 record_deleted`.
  - fails when: шаг 4 §4.1 удалён.
- **T-4** — одна операция доставлена дважды → `version` увеличивается на 1, `RecordChange` содержит одну строку.
  - fails when: проверка `op_id` на шаге 2 §4.1 удалена.
- **T-5** — `client_updated_at` превышает серверное время на 10 мин → ответ `422`, `version` не меняется.
  - fails when: допуск часов увеличен до 15 мин.
- **T-6** — правка поля в офлайне → очередь содержит операцию с этим полем, `body_local` и `body_synced` отличаются только им.
  - fails when: запись `LocalRecord` и вставка операции разнесены по разным транзакциям.
- **T-7** — операция с `base_version`, для которого журнал вычищен → ответ `409 rebase_required`, `version` не меняется.
  - fails when: шаг 7 §4.1 заменён на применение патча целиком.
- **T-8** — две операции одного устройства по одной записи → сервер применяет их в порядке возрастания `seq`.
  - fails when: клиент отправляет операции одной записи параллельно.
- **T-9** — два устройства создают записи с разными `record_id` в офлайне → после синхронизации существуют две записи.
  - fails when: генератор `record_id` заменён на счётчик устройства.

### 9. Решения

- **D-1, 2026-08-05, владелец: архитектор серверной синхронизации:** конфликт правок разрешается слиянием по полям, а не заменой записи. Rejected: замена всего `body` — правка одного поля отменяет правки всех остальных полей.
- **D-2, 2026-08-05, владелец: архитектор серверной синхронизации:** порядок конфликтующих правок определяется парой (`client_updated_at`, `device_id`). Rejected: порядок поступления на сервер — результат зависит от задержки сети и не воспроизводится в тесте.
- **D-3** — см. §5.
- **D-4, 2026-08-05, владелец: архитектор мобильного клиента:** сервер хранит журнал `RecordChange`, а не только текущее состояние. Rejected: хранение одного снимка — шаг 6 §4.1 не может вычислить множество `S`.
- **D-5, 2026-08-05, владелец: архитектор мобильного клиента:** `record_id` назначает устройство-создатель. Rejected: назначение сервером — создание записи в офлайне становится невозможным.

### 10. Открытые вопросы

- **OQ-1** — показывает ли клиент пользователю правку, отброшенную по §5? Blocks: срок хранения операций в статусе `dropped`, раздел интерфейса синхронизации. Owner: продуктовый владелец мобильного клиента.
- **OQ-2** — каково фактическое расхождение часов на устройствах в эксплуатации? Blocks: значение допуска часов в §6. Owner: команда серверной синхронизации.
- **OQ-3** — каков наибольший наблюдаемый офлайн-период устройства? Blocks: TTL маркера удаления и срок хранения `RecordChange`. Owner: команда аналитики.
- **OQ-4** — очищается ли `body` в момент удаления по требованиям приватности? Blocks: `INV-S5`, возможность перебазирования после удаления. Owner: юридическая служба совместно с серверной командой.
- **OQ-5** — применяется ли LWW к вложенным объектам внутри `body` поэлементно? Blocks: определение `changed_fields` для вложенных структур. Owner: архитектор серверной синхронизации.

### 11. Границы раздела

**In scope.**

- поля сущностей `Record`, `RecordChange`, `LocalRecord`, `Operation`, `SyncCursor`
- инварианты, проверяемые тестами `T-1`…`T-9` и ограничениями схемы БД
- правило разрешения конфликта «правка против правки»
- правило разрешения конфликта «удаление против правки»
- состояния операции в очереди клиента и переходы между ними

**Out of scope.**

- схема прикладных полей внутри `body` — раздел «Прикладные сущности»
- транспорт, формат запросов и группировка операций — раздел «Протокол синхронизации»
- аутентификация и выдача токенов устройства — сервис identity
- шифрование локальной базы и защита ключей — раздел «Безопасность клиента»
- миграции схемы локальной базы между версиями клиента — раздел «Версионирование клиента»
- вложения и бинарные файлы записи — раздел «Хранилище файлов»
- совместное редактирование записи несколькими пользователями — вне продукта, `D-5`
- интерфейс уведомления об отброшенной правке — `OQ-1`
- политика повторов и backoff при ошибках сети — раздел «Протокол синхронизации»
