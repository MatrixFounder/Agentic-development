## Модель данных и инварианты

### Цель

Зафиксировать модель данных так, чтобы оба устройства пользователя приходили к одинаковому состоянию записи.

### Границы раздела

In scope: сущности сервера и клиента, поля, инварианты, правило разрешения конфликтов, коды ответа синхронизации.

Out of scope:

- транспорт, формат кадра и повторные попытки — раздел «Протокол синхронизации»;
- схема `payload` предметной области — раздел «Доменная модель»;
- аутентификация и авторизация запроса — раздел «Безопасность»;
- показ конфликта пользователю — раздел «Интерфейс»;
- шифрование локального хранилища и миграции схемы — раздел «Хранилище клиента»;
- совместное редактирование записи несколькими пользователями — не поддерживается системой.

### Определения

- `Tombstone` — состояние записи с `deleted = true`, сохраняемое после удаления.
- `effective_ts` — метка времени операции, равная `min(client_ts, server_received_at)`.
- `Конфликт поля` — состояние, при котором `op.base_version < record.field_meta[f].version`.
- `Конвергенция` — свойство, при котором два устройства с пустыми очередями наблюдают равные `payload` и `deleted`.
- Шкала серьёзности раздела: `Critical`, `Major`, `Minor`.

### Сущности

#### `ServerRecord`

| Поле | Тип | Ограничение |
| :--- | :--- | :--- |
| `id` | UUID | первичный ключ |
| `version` | int64 | ≥ 1 |
| `deleted` | bool | `true` = tombstone |
| `deleted_at` | timestamp UTC \| null | не null при `deleted = true` |
| `updated_at` | timestamp UTC | часы сервера |
| `payload` | object | доменные поля; схема вне раздела |
| `field_meta` | map<field, FieldMeta> | ключ на каждое поле `payload` |
| `applied_op_ids` | set<UUID> | идентификаторы применённых операций |

#### `FieldMeta`

| Поле | Тип | Ограничение |
| :--- | :--- | :--- |
| `version` | int64 | `version` записи на момент принятия поля |
| `ts` | timestamp UTC | `effective_ts` победившей операции |
| `writer` | string | `device_id` победившей операции |

#### `ServerChange`

| Поле | Тип | Ограничение |
| :--- | :--- | :--- |
| `change_seq` | int64 | глобально возрастает на 1 |
| `record_id` | UUID | ссылка на `ServerRecord.id` |
| `version` | int64 | значение после применения |
| `deleted` | bool | значение после применения |
| `server_ts` | timestamp UTC | часы сервера |

#### `LocalRecord`

| Поле | Тип | Ограничение |
| :--- | :--- | :--- |
| `id` | UUID | равен `ServerRecord.id` |
| `base_version` | int64 | ≥ 0; 0 до первой синхронизации |
| `payload` | object | локальное значение с применёнными операциями |
| `deleted_local` | bool | удалено на этом устройстве |
| `last_synced_at` | timestamp UTC \| null | null до первой синхронизации |

#### `Operation`

| Поле | Тип | Ограничение |
| :--- | :--- | :--- |
| `op_id` | UUID | уникален по всем устройствам |
| `record_id` | UUID | ссылка на `LocalRecord.id` |
| `kind` | enum | `create` \| `update` \| `delete` |
| `fields` | map<field, value> | пусто при `kind = delete` |
| `base_version` | int64 | `LocalRecord.base_version` на момент постановки |
| `client_ts` | timestamp UTC | часы устройства |
| `device_seq` | int64 | возрастает в пределах `device_id` |
| `status` | enum | `pending` \| `sent` \| `acked` \| `rejected` |
| `attempts` | int | ≥ 0 |

#### `Device`

| Поле | Тип | Ограничение |
| :--- | :--- | :--- |
| `device_id` | string | уникален у пользователя; сравним побайтово |
| `pull_cursor` | int64 | последний полученный `change_seq` |
| `next_device_seq` | int64 | следующее значение `device_seq` |

### Инварианты

**Сервер.**

- INV-1 — `version` растёт ровно на 1 при каждой принятой операции.
- INV-2 — `version` не уменьшается ни при какой операции.
- INV-3 — `deleted = true` не переходит обратно в `false` для того же `id`.
- INV-4 — `deleted_at` не равно null тогда и только тогда, когда `deleted = true`.
- INV-5 — `field_meta` содержит ключ для каждого поля `payload`.
- INV-6 — `field_meta[f].version` не убывает при применении операций.
- INV-7 — `field_meta[f].ts` не убывает при применении операций.
- INV-8 — `effective_ts` не превышает `server_received_at`.
- INV-9 — повторная доставка `op_id` из `applied_op_ids` оставляет `version` неизменной.
- INV-10 — `change_seq` возрастает строго и не переиспользуется.

**Why (INV-3).** Устройство с непереданной операцией `update` иначе воскрешает запись после удаления.

**Why (INV-8).** Часы устройства задаются пользователем и опережают серверные без ограничения.

**Клиент.**

- INV-11 — `device_seq` строго возрастает в пределах одного `device_id`.
- INV-12 — операции одного `record_id` отправляются в порядке `device_seq`.
- INV-13 — следующая операция по `record_id` отправляется после ответа на предыдущую.
- INV-14 — `base_version` операции не меняется после постановки в очередь.
- INV-15 — операция покидает очередь только со статусом `acked` или `rejected`.
- INV-16 — `LocalRecord.base_version` меняется только ответом сервера или pull.
- INV-17 — `LocalRecord.payload` равен серверному значению плюс поля операций `pending` и `sent`.

**Согласованность.**

- INV-18 — при пустых очередях и равных `pull_cursor` устройства наблюдают равные `payload`.
- INV-19 — при пустых очередях и равных `pull_cursor` устройства наблюдают равный `deleted`.
- INV-20 — итог применения набора операций не зависит от порядка их доставки.

### Правило разрешения конфликтов

Сервер обрабатывает одну операцию по шагам 1–10.

1. Прочитать `ServerRecord` по `op.record_id`. Постусловие: запись прочитана либо отсутствует.
2. При `op.op_id ∈ applied_op_ids` вернуть код `duplicate` и текущее состояние. Постусловие: `version` не изменилась.
3. Вычислить `effective_ts = min(op.client_ts, server_received_at)`. Постусловие: выполнено INV-8.
4. При `record.deleted = true` и `op.kind ≠ delete` вернуть код `gone`. Постусловие: `version` не изменилась.
5. При `op.kind = delete` установить `deleted = true`, `deleted_at = effective_ts`, `version += 1`. Постусловие: запись — tombstone.
6. При `op.kind = create` и отсутствии записи создать её с `version = 1`. Постусловие: `field_meta[f].ts = effective_ts` для каждого поля.
7. При `op.kind = create` и наличии записи обработать её как `update`. Постусловие: вторая запись с тем же `id` не создана.
8. Для `op.kind = update` применить правило поля к каждому `f ∈ op.fields`. Постусловие: каждое поле принято либо отклонено.
9. При наличии хотя бы одного принятого поля увеличить `version` на 1 и записать `updated_at = server_received_at`. Постусловие: выполнены INV-1 и INV-6.
10. Добавить `op_id` в `applied_op_ids` и вернуть `version`, `payload`, список отклонённых полей. Постусловие: повтор шага 2 вернёт `duplicate`.

**Правило поля** для поля `f`.

1. При `op.base_version ≥ record.field_meta[f].version` принять значение. Постусловие: конфликта нет.
2. При `effective_ts > record.field_meta[f].ts` принять значение. Постусловие: поле отмечено принятым.
3. При `effective_ts < record.field_meta[f].ts` отклонить значение. Постусловие: `payload[f]` не изменилось.
4. При равных `ts` и `op.device_id > record.field_meta[f].writer` принять значение. Постусловие: сравнение побайтовое.
5. Иначе отклонить значение. Постусловие: `payload[f]` не изменилось.
6. При принятии записать `field_meta[f] = {version + 1, effective_ts, op.device_id}`. Постусловие: выполнены INV-6 и INV-7.

**Обработка ответа клиентом.**

1. При коде `gone` клиент удаляет `LocalRecord` и отбрасывает остальные операции этого `record_id`. Постусловие: очередь не содержит операций по `record_id`.
2. При отклонённых полях клиент заменяет их значения серверными. Постусловие: выполнен INV-17.
3. При коде `duplicate` клиент помечает операцию `acked`. Постусловие: повторная отправка не происходит.

### Удаление на одном устройстве и правка на другом

Устройство A выполняет `delete`, устройство B выполняет `update` того же `record_id`.

- **Порядок D1** — сначала доставлен `delete` A. Шаг 4 возвращает B код `gone`; запись остаётся tombstone.
- **Порядок D2** — сначала доставлен `update` B. Поля приняты, затем шаг 5 применяет `delete` A без сравнения `base_version`.

Оба порядка дают `deleted = true`. Правка B не сохраняется ни в одном порядке.

**Why.** Шаг 5 игнорирует `base_version`, а шаг 4 отклоняет `update` по tombstone; вместе они делают исход независимым от порядка.

### Решения

- **DEC-1, 2026-08-05, архитектор синхронизации:** `delete` доминирует над `update` в обоих порядках доставки. Rejected: воскрешение записи более поздней правкой — исход зависит от порядка доставки, INV-20 не выполняется.
- **DEC-2, 2026-08-05, архитектор синхронизации:** конфликт разрешается по полям, а не по записи целиком. Rejected: разрешение по записи — отбрасывает и непересекающиеся поля проигравшей операции.
- **DEC-3, 2026-08-05, архитектор синхронизации:** `client_ts` ограничивается сверху временем приёма на сервере. Rejected: доверие `client_ts` без ограничения — устройство с часами на год вперёд выигрывает все конфликты.
- **DEC-4, 2026-08-05, архитектор синхронизации:** ничья по `ts` разрешается сравнением `device_id`. Rejected: разрешение по порядку приёма — исход зависит от сетевых задержек, INV-20 не выполняется.

### Риски

- **R1** — часы устройства отстают от серверных → его правки проигрывают конфликты поля (обнаруживается тестом T-C2 и метрикой `clock_offset_seconds`). Severity: `Major`.
- **R2** — tombstone удалён до синхронизации устройства → `create` создаёт запись заново (обнаруживается тестом T-D3). Severity: `Critical`. Зависит от OQ-1.
- **R3** — `applied_op_ids` очищен до повторной доставки `op_id` → операция применяется дважды, `version` растёт на 2 (обнаруживается тестом T-I1). Severity: `Major`. Зависит от OQ-3.
- **R4** — длительный офлайн наполняет очередь операций → исчерпание квоты локального хранилища (обнаруживается метрикой `queue_length`). Severity: `Major`. Зависит от OQ-2.
- **R5** — клиент отправляет операции одного `record_id` параллельно → `base_version` второй операции описывает устаревшее состояние (обнаруживается тестом T-Q1). Severity: `Major`.

### Тестовые обязательства

- **T-D1** — `delete` A применён, затем `update` B → код `gone`, `version` не изменилась; fails when удалён шаг 4.
- **T-D2** — `update` B применён, затем `delete` A с устаревшим `base_version` → `deleted = true`; fails when шаг 5 начинает сравнивать `base_version`.
- **T-D3** — `create` с `id` удалённой записи → код `gone`, вторая запись не создана; fails when шаг 4 пропускает `kind = create`.
- **T-C1** — два `update` с непересекающимися `fields` → оба приняты, `version` выросла на 2; fails when правило поля заменено на сравнение по записи.
- **T-C2** — два `update` одного поля с разными `effective_ts` → принят больший; fails when `>` заменено на `≥` в шаге 2 правила поля.
- **T-C3** — два `update` одного поля с равными `effective_ts` → принят больший `device_id`; fails when удалён шаг 4 правила поля.
- **T-C4** — `client_ts` на год впереди → `effective_ts = server_received_at`; fails when удалён `min` в шаге 3.
- **T-I1** — повторная доставка `op_id` → код `duplicate`, `version` не изменилась; fails when шаг 2 не читает `applied_op_ids`.
- **T-K1** — один набор из четырёх операций в двух порядках доставки → равные `payload` и `deleted`; fails when нарушен любой из INV-6, INV-7, DEC-4.
- **T-Q1** — две операции одного `record_id` в очереди → вторая отправлена после ответа на первую; fails when удалён INV-13.
- **T-Q2** — ответ `gone` по `record_id` → очередь не содержит операций этого `record_id`; fails when удалён шаг 1 обработки ответа.

### Открытые вопросы

- **OQ-1** — Каков срок хранения tombstone на сервере? Кандидат: `TTL = 90 суток = 3 × 30 суток допустимого офлайна`; измерено — нет данных; применено 90 суток как потолок. Blocks: INV-3, R2, T-D3. Owner: архитектор бэкенда.
- **OQ-2** — Каков предел длины очереди операций на устройстве и поведение при его достижении? Blocks: R4, поведение клиента при переполнении. Owner: архитектор мобильного клиента.
- **OQ-3** — Хранится ли `applied_op_ids` бессрочно или с TTL? Blocks: INV-9, R3, T-I1. Owner: архитектор бэкенда.
- **OQ-4** — Какие часы дают `client_ts`: стенные часы устройства или монотонные с привязкой к серверному времени? Blocks: R1, T-C4. Owner: архитектор мобильного клиента.
- **OQ-5** — Сохраняет ли сервер отклонённые значения полей для последующего разбора? Blocks: состав ответа шага 10, объём хранилища. Owner: архитектор бэкенда.
