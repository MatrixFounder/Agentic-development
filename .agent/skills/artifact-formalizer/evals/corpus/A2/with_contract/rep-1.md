## 1. Проблема

Хранилище сессий — модуль в памяти процесса приложения. Из этого следуют четыре наблюдаемых факта.

| Код | Наблюдаемый факт | Как проверяется сейчас |
| :--- | :--- | :--- |
| P-1 | Рестарт процесса удаляет все его сессии | Деплой возвращает пользователей на форму входа |
| P-2 | Балансировщик закрепляет клиента за инстансом (sticky sessions) | Конфигурация балансировщика содержит правило закрепления |
| P-3 | Отказ инстанса завершает сессии его клиентов | Клиент после переключения попадает на форму входа |
| P-4 | Новый инстанс не обслуживает существующие сессии | Расширение пула не разгружает загруженный инстанс |

Количество активных сессий на момент деплоя не измерено. Смотри `OQ-1`.

---

## 2. Цели

- **G-1.** Перенести сессии в Redis так, чтобы рестарт инстанса не завершал активные сессии.
- **G-2.** Снять закрепление клиента за инстансом так, чтобы любой инстанс обслуживал любую сессию.
- **G-3.** Задать поведение при недоступности Redis так, чтобы деградация была наблюдаемой и обратимой.

---

## 3. Область работ

### 3.1 В области работ

Интерфейс `SessionStore`; реализация `RedisSessionStore`; формат записи и ключа; режимы совместимости
на время перехода; политика срока жизни; поведение при ошибках Redis; метрики и алерты; конфигурация
Redis-инстанса под сессии; тесты из §8.

### 3.2 Вне области работ

| Код | Что не входит | Кто несёт это вместо нас |
| :--- | :--- | :--- |
| OS-1 | Смена формата и энтропии `sid` | команда безопасности, отдельная задача |
| OS-2 | Отзыв всех сессий пользователя одной операцией | продуктовая команда, бэклог `AUTH-88` |
| OS-3 | Переход на JWT или на stateless-аутентификацию | архитектурный комитет |
| OS-4 | Кластеризация Redis и мультирегиональная репликация | SRE, задача `INFRA-210` |

## 4. Термины

- **Сессия** — набор серверных данных, который идентифицируется значением `sid` из cookie.
- **`sid`** — строковый идентификатор сессии, передаваемый клиентом в cookie.
- **Idle TTL** — интервал бездействия, по истечении которого сессия перестаёт существовать.
- **Absolute TTL** — интервал от создания сессии, по истечении которого сессия перестаёт существовать.
- **`circuit breaker`** — компонент, который прекращает сетевые вызовы после порога ошибок. Термин
  установлен: он входит в публичный API `Resilience4j` и `Polly`.
- **Dual-режим** — режим работы `SessionStore`, при котором запись идёт в оба хранилища.
- **Важность `Critical`** — уровень, требующий немедленной реакции дежурного.
- **Важность `Major`** — уровень, требующий реакции в рабочее время текущего дня.
- **Важность `Minor`** — уровень, требующий записи в бэклог.

## 5. Требования

### 5.1 Интерфейс, ключ и формат записи

- **R-01.** Прикладной код обращается к сессиям только через интерфейс `SessionStore`.
- **R-02.** `SessionStore` объявляет операции `get(sid)`, `set(sid, data)`, `touch(sid)`, `destroy(sid)`.
- **R-03.** Существуют две реализации: `MemorySessionStore` и `RedisSessionStore`.
- **R-04.** Ключ в Redis имеет вид `sess:v1:<hex(sha256(sid))>`.
- **R-05.** Значение ключа — документ JSON в кодировке UTF-8.
- **R-06.** Документ содержит поля `v`, `uid`, `created_at`, `last_seen_at`, `data`.
- **R-07.** Поле `v` при записи равно `1`.
- **R-08.** Читатель при `v`, отличном от `1`, возвращает «сессия отсутствует».
- **R-09.** Сериализованный документ длиной свыше 32 KiB не записывается.
- **R-10.** Попытка записи документа свыше 32 KiB возвращает ошибку `SessionTooLarge`.
- **R-11.** `set` вызывается только при изменённом содержимом сессии.
- **R-12.** Параллельные записи по одному `sid` разрешаются правилом «последняя запись побеждает».

**Why (R-04).** Дамп Redis не содержит значений cookie, поэтому чтение дампа не даёт готового `sid`.

**Why (R-11).** Запись на каждом запросе умножает нагрузку на Redis на число статических подзапросов.

### 5.2 Совместимость на время перехода

- **R-13.** Имя, домен, путь и флаги cookie сессии не изменяются.
- **R-14.** Формат значения `sid` не изменяется.
- **R-15.** Флаг `SESSION_STORE_MODE` принимает значения `memory`, `dual-read-memory`, `dual-read-redis`, `redis`.
- **R-16.** Значение флага перечитывается процессом не реже одного раза в 30 секунд.
- **R-17.** В режимах `dual-read-memory` и `dual-read-redis` запись идёт в оба хранилища.
- **R-18.** В `dual-read-memory` чтение идёт из памяти, при промахе — из Redis.
- **R-19.** В `dual-read-redis` чтение идёт из Redis, при промахе — из памяти.
- **R-20.** Сессия, найденная в памяти в режиме `dual-read-redis`, записывается в Redis тем же запросом.
- **R-21.** В режиме `redis` вызовы `MemorySessionStore` отсутствуют.
- **R-22.** Ошибка записи в Redis в dual-режиме не отменяет ответ; ошибка увеличивает счётчик `session_store_errors_total`.
- **R-23.** Ошибка записи в память в dual-режиме не отменяет ответ.
- **R-24.** Переход между режимами выполняется в порядке `memory` → `dual-read-memory` → `dual-read-redis` → `redis`.
- **R-25.** Режим `dual-read-redis` удерживается не менее 24 часов до перехода в `redis`.

**Why (R-16).** Возврат к предыдущему режиму не ждёт цикла деплоя.

**Why (R-25).** За 24 часа все сессии, существовавшие только в памяти, достигают Absolute TTL.

### 5.3 Поведение при недоступности Redis

Недоступность Redis — состояние, при котором операция завершается таймаутом, ошибкой соединения или
ответом-ошибкой.

- **R-26.** Таймаут одной операции к Redis — 100 ms.
- **R-27.** Операция повторяется однократно; суммарный бюджет операции — 200 ms.
- **R-28.** `circuit breaker` открывается при доле ошибок 50 % и более на окне из 20 операций.
- **R-29.** Открытый `circuit breaker` возвращает ошибку без сетевого вызова.
- **R-30.** `circuit breaker` переходит в half-open через 5 секунд и пропускает 3 пробных операции.
- **R-31.** Ошибка чтения сессии возвращает ответ `503` с заголовком `Retry-After: 5`.
- **R-32.** Ответ при ошибке чтения не содержит заголовка `Set-Cookie`.
- **R-33.** Ошибка записи сессии при входе возвращает `503`; сессия не создаётся.
- **R-34.** Резервный переход на `MemorySessionStore` при ошибке Redis отсутствует.
- **R-35.** Маршруты из списка `SESSION_ANONYMOUS_ROUTES` обслуживаются без обращения к хранилищу.
- **R-36.** Список `SESSION_ANONYMOUS_ROUTES` содержит `/health`, `/health/ready`, `/login`, `/static/*`.
- **R-37.** Проба готовности `/health/ready` не обращается к Redis.

**Why (R-31 и R-32).** Редирект на форму входа порождает повторные входы и добавляет нагрузку
на деградировавшую систему; сохранённая cookie позволяет продолжить сессию после восстановления.

**Why (R-34).** Память возвращает закрепление клиента за инстансом — состояние `P-2`, которое задача устраняет.

**Why (R-37).** Отказ Redis снял бы все инстансы с балансировки и превратил частичную деградацию в полный отказ.

### 5.4 Срок жизни сессии

- **R-38.** Инстанс Redis выделен под сессии; кэш и очереди используют другие инстансы.
- **R-39.** Idle TTL равен 30 минутам и отсчитывается от `last_seen_at`.
- **R-40.** Absolute TTL равен 12 часам и отсчитывается от `created_at`.
- **R-41.** Absolute TTL не продлевается ни одной операцией.
- **R-42.** TTL ключа равен минимуму из остатка Idle TTL и остатка Absolute TTL.
- **R-43.** `touch` продлевает TTL, если остаток Idle TTL меньше 15 минут.
- **R-44.** Читатель отвергает документ, у которого `created_at` старше Absolute TTL.
- **R-45.** Вход, смена пароля и смена роли порождают новый `sid`; прежний ключ удаляется.
- **R-46.** Выход удаляет ключ и возвращает cookie с `Max-Age=0`.
- **R-47.** Политика вытеснения Redis-инстанса — `noeviction`.
- **R-48.** Персистентность Redis-инстанса — AOF с `appendfsync everysec`.

**Why (R-43).** Продление на каждом запросе даёт одну запись на запрос; порог в половину Idle TTL
ограничивает частоту записи одним разом в 15 минут на активную сессию.

**Why (R-47).** `allkeys-lru` завершал бы произвольные сессии при заполнении памяти.

**Why (R-44).** Ключ, записанный до изменения политики, может нести TTL больше Absolute TTL.

### 5.5 Наблюдаемость

- **R-49.** Приложение публикует гистограмму `session_store_op_duration_seconds` с метками `op` и `outcome`.
- **R-50.** Приложение публикует счётчик `session_store_errors_total` с меткой `reason`.
- **R-51.** Приложение публикует показатель `session_breaker_state` со значениями `0`, `1`, `2`.
- **R-52.** Логи не содержат `sid` и значение cookie сессии.
- **R-53.** Логи содержат первые 8 символов `hex(sha256(sid))`.
- **R-54.** Алерт `SessionStoreErrorRate` срабатывает при доле ошибок 1 % на окне 5 минут; важность `Major`.
- **R-55.** Алерт `SessionBreakerOpen` срабатывает при открытом `circuit breaker` дольше 60 секунд; важность `Critical`.
- **R-56.** Алерт `SessionRedisMemory` срабатывает при `used_memory` выше 70 % от `maxmemory`; важность `Major`.

### 5.6 Безопасность и конфигурация

- **R-57.** Соединение к Redis использует TLS.
- **R-58.** Аутентификация к Redis выполняется командой `AUTH` с паролем из секрет-хранилища.
- **R-59.** Пароль Redis отсутствует в репозитории и в образе контейнера.
- **R-60.** Сетевой доступ к Redis-инстансу открыт только с адресов приложения.

## 7. Сценарии использования

### UC-1 — Запрос с действующей сессией

1. Клиент отправляет запрос с cookie `sid`. Постусловие: обработчик получил `sid`.
2. `RedisSessionStore.get` читает ключ `sess:v1:<hash>`. Постусловие: документ получен.
3. Читатель сверяет `v` и `created_at` с `R-08` и `R-44`. Постусловие: сессия признана действующей.
4. Обработчик выполняет прикладную логику. Постусловие: ответ сформирован.
5. `touch` продлевает TTL при выполнении условия `R-43`. Постусловие: TTL ключа соответствует `R-42`.

### UC-2 — Вход пользователя

1. Клиент отправляет учётные данные на `/login`. Постусловие: данные проверены.
2. Приложение порождает новый `sid`. Постусловие: прежний `sid` клиента больше не используется.
3. `set` записывает документ с `created_at` текущего момента. Постусловие: ключ существует в Redis.
4. Ответ возвращает cookie с новым `sid`. Постусловие: клиент хранит новый `sid`.

### UC-3 — Выход пользователя

1. Клиент вызывает `/logout`. Постусловие: `sid` получен.
2. `destroy` удаляет ключ. Постусловие: ключ отсутствует в Redis.
3. Ответ возвращает cookie с `Max-Age=0`. Постусловие: клиент удалил cookie.

### UC-4 — Деплой инстанса

1. Оркестратор останавливает инстанс. Постусловие: процесс завершён.
2. Балансировщик направляет запросы клиента на другой инстанс. Постусловие: запрос принят.
3. Другой инстанс читает ту же сессию из Redis. Постусловие: пользователь не видит форму входа.

### UC-5 — Redis недоступен

1. `get` завершается таймаутом дважды. Постусловие: счётчик ошибок увеличен.
2. `circuit breaker` достигает порога `R-28`. Постусловие: состояние `open`.
3. Приложение возвращает `503` с `Retry-After: 5`. Постусловие: cookie клиента не изменена.
4. Алерт `SessionBreakerOpen` срабатывает через 60 секунд. Постусловие: дежурный уведомлён.
5. Redis отвечает на пробные операции half-open. Постусловие: состояние `closed`, ответы `200`.

### UC-6 — Истечение по бездействию

1. Клиент не отправляет запросов 30 минут. Постусловие: TTL ключа истёк.
2. Клиент отправляет запрос. Постусловие: `get` возвращает «сессия отсутствует».
3. Приложение возвращает редирект на `/login`. Постусловие: клиент видит форму входа.

### UC-7 — Достижение абсолютного срока

1. Клиент работает без перерывов 12 часов. Постусловие: `created_at` старше Absolute TTL.
2. `get` читает документ и применяет `R-44`. Постусловие: сессия признана отсутствующей.
3. Приложение возвращает редирект на `/login`. Постусловие: клиент видит форму входа.

### UC-8 — Переход `dual-read-memory` → `dual-read-redis`

1. Оператор меняет значение `SESSION_STORE_MODE`. Постусловие: новое значение в конфигурации.
2. Инстансы перечитывают флаг в течение 30 секунд. Постусловие: чтение идёт из Redis.
3. Сессии, отсутствующие в Redis, читаются из памяти и копируются. Постусловие: доля промахов Redis падает.
4. Оператор наблюдает долю промахов на дашборде. Постусловие: доля промахов ниже 1 % — условие перехода к `redis`.

### UC-9 — Возврат к предыдущему режиму

1. Оператор задаёт `SESSION_STORE_MODE=dual-read-memory`. Постусловие: значение записано.
2. Инстансы перечитывают флаг в течение 30 секунд. Постусловие: чтение идёт из памяти.
3. Сессии, созданные в режиме `redis`, читаются из Redis при промахе памяти. Постусловие: активные сессии сохранены.

### UC-10 — Горизонтальное масштабирование

1. Оркестратор добавляет инстанс в пул. Постусловие: инстанс принимает запросы.
2. Балансировщик распределяет запросы без правила закрепления. Постусловие: запросы одного клиента идут на разные инстансы.
3. Каждый инстанс читает сессию из Redis. Постусловие: ответы одинаковы по содержанию сессии.

## 8. Режимы отказа

| Код | Условие → наблюдаемый исход | Обнаруживается |
| :--- | :--- | :--- |
| RK-1 | Redis недоступен → все запросы с сессией отвечают `503` | `AC-06`, алерт `SessionBreakerOpen` |
| RK-2 | Память Redis исчерпана при `noeviction` → `set` отвечает ошибкой, вход возвращает `503` | `AC-11`, алерт `SessionRedisMemory` |
| RK-3 | Два параллельных запроса пишут сессию → изменения первого запроса потеряны | `AC-12` |
| RK-4 | Сессия превышает 32 KiB → `set` возвращает `SessionTooLarge`, данные не сохраняются | `AC-05` |
| RK-5 | Переход в `redis` раньше 24 часов → сессии из памяти теряются при рестарте | `AC-14`, гейт релиза `G-142-3` |
| RK-6 | Latency Redis превышает 100 ms → доля таймаутов растёт, breaker открывается | `AC-07`, алерт `SessionStoreErrorRate` |
| RK-7 | Пароль Redis попал в образ → чтение образа даёт доступ к сессиям | `AC-18` |
| RK-8 | Правило закрепления снято до режима `redis` → часть запросов не находит сессию | порядок работ `OS-6` |

## 9. Критерии приёмки

Формат: `<идентификатор> — <вход> → <утверждаемый исход>; ломается при <мутации>`.

- **AC-01** — `set` затем `get` по тому же `sid` → возвращается записанный документ; ломается при удалении префикса `sess:v1:` из ключа.
- **AC-02** — `get` по `sid`, ключ которого удалён → возвращается «сессия отсутствует»; ломается при возврате пустого документа вместо признака отсутствия.
- **AC-03** — документ с полем `v: 2` → `get` возвращает «сессия отсутствует»; ломается при удалении проверки `R-08`.
- **AC-04** — ключ в Redis для известного `sid` → имя ключа равно `sess:v1:<hex(sha256(sid))>`; ломается при подстановке `sid` в ключ без хеширования.
- **AC-05** — `set` с документом 33 KiB → ошибка `SessionTooLarge`, ключ не создан; ломается при повышении лимита в коде.
- **AC-06** — `get` при остановленном Redis → ответ `503` с `Retry-After: 5`, заголовок `Set-Cookie` отсутствует; ломается при замене ответа на редирект `302`.
- **AC-07** — 20 операций с задержкой 150 ms → `session_breaker_state` равен `1`; ломается при повышении таймаута выше 150 ms.
- **AC-08** — открытый `circuit breaker`, затем 5 секунд без вызовов → состояние `2`, выполняются 3 пробные операции; ломается при удалении перехода в half-open.
- **AC-09** — `POST /login` при остановленном Redis → ответ `503`, сессия не создана; ломается при добавлении записи в память.
- **AC-10** — `GET /health/ready` при остановленном Redis → ответ `200`; ломается при добавлении `PING` в пробу готовности.
- **AC-11** — Redis с заполненной `maxmemory` → `set` возвращает ошибку, ключи существующих сессий не удалены; ломается при смене политики на `allkeys-lru`.
- **AC-12** — два параллельных `set` по одному `sid` → в Redis остаётся документ второй записи; ломается при слиянии полей на стороне клиента Redis.
- **AC-13** — режим `dual-read-redis`, сессия только в памяти → `get` возвращает документ, ключ появляется в Redis; ломается при удалении шага копирования `R-20`.
- **AC-14** — режим `redis`, трассировка запроса → вызовы `MemorySessionStore` отсутствуют; ломается при возврате резервного пути на память.
- **AC-15** — смена `SESSION_STORE_MODE` без рестарта → новое поведение наблюдается не позже чем через 30 секунд; ломается при чтении флага только на старте процесса.
- **AC-16** — сессия с `last_seen_at` 31 минуту назад → `get` возвращает «сессия отсутствует»; ломается при повышении Idle TTL.
- **AC-17** — сессия с `created_at` 13 часов назад и `last_seen_at` минуту назад → `get` возвращает «сессия отсутствует»; ломается при удалении проверки `R-44`.
- **AC-18** — `touch` при остатке TTL 20 минут → TTL ключа не изменён; ломается при удалении порога `R-43`.
- **AC-19** — успешный вход по существующей сессии → прежний ключ удалён, cookie содержит новый `sid`; ломается при повторном использовании прежнего `sid`.
- **AC-20** — `POST /logout` → ключ отсутствует в Redis, cookie содержит `Max-Age=0`; ломается при удалении вызова `destroy`.
- **AC-21** — журнал за прогон нагрузочного теста → строки не содержат значений `sid`; ломается при логировании cookie целиком.
- **AC-22** — образ контейнера и репозиторий → пароль Redis не найден поиском по строке; ломается при переносе пароля в файл конфигурации образа.
- **AC-23** — два инстанса без правила закрепления, 100 запросов одного клиента → все ответы содержат одинаковые данные сессии; ломается при включении локального кэша сессии без инвалидации.

Проверки `AC-01` … `AC-20` — автоматические тесты в CI. Проверки `AC-21` … `AC-23` — шаги приёмочного
прогона на стенде, выполняются вручную и фиксируются в отчёте релиза.

## 10. Принятые решения

- **D-1, 2026-08-05, техлид платформы:** доступ к сессиям идёт через интерфейс `SessionStore` с двумя
  реализациями. Отклонено: прямые вызовы клиента Redis из обработчиков — тесты `AC-13` и `AC-14`
  становятся невыполнимыми без сетевого Redis.
- **D-2, 2026-08-05, техлид платформы:** формат значения — JSON. Отклонено: MessagePack — выигрыш
  размера не измерен, а чтение ключа в консоли Redis перестаёт быть однокомандным.
- **D-3, 2026-08-05, команда безопасности:** ключом служит `hex(sha256(sid))`. Отклонено: `sid`
  в открытом виде — дамп Redis тогда содержит готовые значения cookie.
- **D-4, 2026-08-05, техлид платформы:** резервный переход на память при отказе Redis не реализуется.
  Отклонено: fallback в память — он восстанавливает закрепление за инстансом, то есть факт `P-2`.
- **D-5, 2026-08-05, техлид платформы:** ошибка чтения сессии даёт `503`, а не редирект на вход.
  Отклонено: редирект на `/login` — он порождает повторные входы поверх деградировавшего Redis.
- **D-6, 2026-08-05, SRE:** проба готовности не обращается к Redis. Отклонено: `PING` в `/health/ready` —
  отказ Redis тогда снимает с балансировки все инстансы одновременно.
- **D-7, 2026-08-05, SRE:** политика вытеснения — `noeviction`, персистентность — AOF `everysec`.
  Отклонено: `allkeys-lru` — вытеснение завершает произвольные сессии без события в журнале.
- **D-8, 2026-08-05, SRE:** сессии живут на выделенном инстансе Redis. Отклонено: общий инстанс с кэшем —
  кэш и сессии тогда делят один бюджет памяти и одну политику вытеснения.
- **D-9, 2026-08-05, техлид платформы:** переход выполняется четырьмя режимами флага `SESSION_STORE_MODE`.
  Отклонено: одномоментное переключение — возврат тогда завершает все сессии, созданные после переключения.
- **D-10, 2026-08-05, техлид платформы:** конфликт параллельных записей разрешается правилом
  «последняя запись побеждает». Отклонено: слияние по полям — стоимость реализации не покрыта
  измеренной частотой конфликтов, риск зафиксирован как `RK-3`.

## 11. Открытые вопросы

- **OQ-1** — Сколько активных сессий существует в момент деплоя? Блокирует: расчёт `maxmemory` для
  Redis-инстанса и порог алерта `SessionRedisMemory`. Владелец: SRE.
- **OQ-2** — Каков измеренный p99 latency операции к Redis из сети приложения? Блокирует: подтверждение
  таймаута 100 ms в `R-26`. Владелец: SRE.
- **OQ-3** — Каков p99 размера сериализованной сессии сегодня? Блокирует: подтверждение лимита 32 KiB
  в `R-09`. Владелец: техлид платформы.
- **OQ-4** — Согласованы ли значения Idle TTL 30 минут и Absolute TTL 12 часов с текущим поведением
  и с требованиями регулятора? Блокирует: `R-39` и `R-40`. Владелец: продуктовый владелец.
- **OQ-5** — Какова энтропия текущего значения `sid`? Блокирует: решение о том, достаточно ли `R-14`
  для сохранения текущего уровня защиты. Владелец: команда безопасности.
- **OQ-6** — Приемлем ли ответ `503` для мобильного клиента, или он показывает пользователю экран
  ошибки без повтора? Блокирует: `R-31`. Владелец: команда мобильной разработки.
- **OQ-7** — Какие маршруты кроме перечисленных в `R-36` работают без сессии? Блокирует: полноту
  списка `SESSION_ANONYMOUS_ROUTES`. Владелец: техлид платформы.
- **OQ-8** — Какой сценарий восстановления применяется при потере данных Redis-инстанса целиком?
  Блокирует: план работ `INFRA-210`. Владелец: SRE.
- **OQ-9** — Требуется ли отзыв всех сессий пользователя при смене пароля на других устройствах?
  Блокирует: границу `OS-2`. Владелец: команда безопасности.
