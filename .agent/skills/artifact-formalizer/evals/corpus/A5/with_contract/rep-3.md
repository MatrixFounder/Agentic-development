## Модель данных и инварианты

### 1. Термины

- `Record` — серверная запись, которая хранит текущее состояние и номер версии.
- `LocalRecord` — копия `Record` на устройстве, доступная без сети.
- `Operation` — элемент очереди устройства, описывающий одно изменение одной записи.
- `base_version` — значение `Record.version`, от которого построено изменение.
- `tombstone` — состояние `Record` с `deleted = true` и пустым `body`.
- `rejected_fields` — поля операции, которые сервер не применил.

Раздел описывает записи одного `owner_id`, изменяемые несколькими устройствами этого пользователя.

### 2. Сущности и поля

#### 2.1 `Record` (сервер)

| Поле | Тип | Ограничение |
| :--- | :--- | :--- |
| `record_id` | UUIDv7 | первичный ключ; назначает устройство-создатель |
| `owner_id` | UUID | не null |
| `version` | int64 | ≥ 1; назначает сервер |
| `body` | JSON-объект | пуст при `deleted = true` |
| `field_versions` | map<string, int64> | ключ — путь поля `body` |
| `deleted` | bool | переход только `false → true` |
| `deleted_at` | timestamp UTC | не null при `deleted = true` |
| `updated_at` | timestamp UTC | часы сервера |
| `last_writer` | UUID | `device_id` последней применённой операции |
| `seq` | int64 | позиция в журнале изменений владельца |

#### 2.2 `LocalRecord` (устройство)

| Поле | Тип | Ограничение |
| :--- | :--- | :--- |
| `record_id` | UUIDv7 | первичный ключ |
| `base_version` | int64 | 0 до первого подтверждения сервера |
| `body` | JSON-объект | состояние, показываемое пользователю |
| `deleted_locally` | bool | локальное удаление до подтверждения |
| `has_pending` | bool | вычисляется: очередь содержит операции этой записи |
| `synced_at` | timestamp UTC | момент последнего подтверждения |

#### 2.3 `Operation` (очередь устройства)

| Поле | Тип | Ограничение |
| :--- | :--- | :--- |
| `op_id` | UUIDv7 | первичный ключ; порядок равен порядку постановки |
| `record_id` | UUIDv7 | внешний ключ на `LocalRecord` |
| `device_id` | UUID | устройство-автор |
| `kind` | enum | `create` \| `update` \| `delete` |
| `base_version` | int64 | копия `LocalRecord.base_version` на момент постановки |
| `patch` | map<string, value> | пуст при `kind = delete` |
| `state` | enum | `queued` \| `sent` \| `applied` \| `rebased` \| `dropped` |
| `attempts` | int | число отправок |
| `created_at` | timestamp UTC | часы устройства; в разрешении конфликтов не участвует |

Переходы `state`:

| Из | В | Условие |
| :--- | :--- | :--- |
| `queued` | `sent` | устройство отправило операцию |
| `sent` | `queued` | ответ не получен; `attempts` увеличен на 1 |
| `sent` | `applied` | сервер вернул `resolution = applied` |
| `sent` | `rebased` | сервер вернул `resolution = rebased` |
| `sent` | `dropped` | сервер вернул `dropped_by_tombstone` или `invalid_base` |

Состояния `applied`, `rebased`, `dropped` терминальные.

#### 2.4 `SyncCursor` (устройство)

| Поле | Тип | Ограничение |
| :--- | :--- | :--- |
| `device_id` | UUID | первичный ключ |
| `server_seq` | int64 | последняя принятая позиция журнала |
| `synced_at` | timestamp UTC | момент последнего чтения журнала |

#### 2.5 `ConflictLog` (устройство)

| Поле | Тип | Ограничение |
| :--- | :--- | :--- |
| `conflict_id` | UUIDv7 | первичный ключ |
| `op_id` | UUIDv7 | операция, породившая запись |
| `record_id` | UUIDv7 | запись, к которой относится операция |
| `resolution` | enum | `applied` \| `rebased` \| `dropped_by_tombstone` \| `invalid_base` |
| `rejected_fields` | list<string> | пуст при `resolution = applied` |
| `resolved_at` | timestamp UTC | момент записи ответа |

### 3. Инварианты

| ID | Инвариант | Обнаруживается |
| :--- | :--- | :--- |
| INV-1 | `record_id` уникален среди всех записей владельца | уникальный индекс сервера |
| INV-2 | сервер увеличивает `version` ровно на 1 за применение | T-DM-3 |
| INV-3 | `version` не уменьшается | T-DM-6 |
| INV-4 | `deleted` переходит только из `false` в `true` | T-DM-1 |
| INV-5 | при `deleted = true` поля `body` и `field_versions` пусты | T-DM-2 |
| INV-6 | `LocalRecord.base_version` не превышает `Record.version` | T-DM-6 |
| INV-7 | очередь содержит не более одной операции `sent` на `record_id` | инвариант очереди, проверка при отправке |
| INV-8 | операция покидает очередь после записи в `ConflictLog` | T-DM-7 |
| INV-9 | повторная отправка того же `op_id` не изменяет `Record` | T-DM-3 |
| INV-10 | разрешение конфликтов не читает `Operation.created_at` | обзор кода шага 6 |
| INV-11 | `SyncCursor.server_seq` не убывает | тест курсора |
| INV-12 | каждый ключ `field_versions` присутствует в `body` | проверка целостности на сервере |
| INV-13 | `field_versions[поле]` не превышает `version` | проверка целостности на сервере |
| INV-14 | два устройства после полной синхронизации наблюдают одинаковые `body` и `deleted` | T-DM-1, T-DM-2, T-DM-4, T-DM-5 |

`version` двух устройств совпадает только после чтения одного и того же `server_seq`. Номера версий между устройствами не сравниваются.

### 4. Правило разрешения конфликтов

Порядок применения определяет сервер. Устройство не разрешает конфликты самостоятельно.

1. Устройство отправляет операции одной записи по возрастанию `op_id`, по одной. Постусловие: выполнен INV-7.
2. Сервер ищет `op_id` в журнале применённых операций. Постусловие: найденный `op_id` возвращает сохранённый ответ, `version` не изменён.
3. Сервер читает `Record.deleted`. Постусловие: при `deleted = true` результат определяет шаг 8.
4. Сервер сравнивает `Operation.base_version` с `Record.version`. Постусловие: выбрана ветка 5, 6 или 9.
5. При `base_version = version` сервер применяет `patch` целиком. Постусловие: `version` увеличен на 1, ключи `patch` записаны в `field_versions`, `resolution = applied`.
6. При `base_version < version` сервер собирает множество `S` полей с `field_versions[поле] > base_version`. Постусловие: `S` вычислено по данным сервера.
7. Сервер применяет поля `patch` вне `S` и отбрасывает поля из `S`. Постусловие: `version` увеличен на 1, отброшенные поля возвращены как `rejected_fields`, `resolution = rebased`.
8. При `Record.deleted = true` сервер отбрасывает операцию с `kind` из {`create`, `update`}. Постусловие: `version` не изменён, `resolution = dropped_by_tombstone`.
9. При `base_version > version` сервер отвечает `invalid_base`. Постусловие: устройство перечитывает запись из журнала и очищает её операции.
10. При `kind = delete` сервер ставит `deleted = true`, очищает `body` и `field_versions`, увеличивает `version` на 1. Постусловие: запись — `tombstone`.
11. Устройство записывает ответ в `ConflictLog` и снимает операцию с очереди. Постусловие: очередь не содержит терминальных операций.
12. Устройство присваивает `LocalRecord.base_version` возвращённое `version`. Постусловие: выполнен INV-6.

`create` с уже существующим `record_id` сервер обрабатывает шагами 6–7 при `base_version = 0`.

**Why.** Повтор `create` после потери ответа неотличим от нового создания. Обработка через шаг 6 сохраняет поля, изменённые другим устройством.

Пересечение по одному полю разрешается в пользу изменения, применённого сервером раньше.

**Why.** Часы устройств сервер не сверяет ⇒ порядок по `created_at` не наблюдаем и не воспроизводим в тесте.

### 5. Удаление на одном устройстве и правка на другом

Устройство A ставит `delete` с `base_version = v`. Устройство B ставит `update` с `base_version = v`.

| Порядок прихода | Шаги | Итог `Record` |
| :--- | :--- | :--- |
| `delete`, затем `update` | 10, затем 8 | `deleted = true`, `body` пуст, `version = v+1` |
| `update`, затем `delete` | 5 или 7, затем 10 | `deleted = true`, `body` пуст, `version = v+2` |

Наблюдаемое состояние совпадает в обоих порядках: `deleted = true` и пустой `body`. Номер `version` зависит от порядка доставки.

Устройство B получает `resolution = dropped_by_tombstone` и пустой `rejected_fields` в первом порядке.

Восстановление удалённой записи выполняется как создание записи с новым `record_id`.

Локальное удаление записи с `base_version = 0` без операций в состоянии `sent` удаляет `LocalRecord` и её операции из очереди. Постусловие: сервер не получает запросов по этому `record_id`.

Локальное удаление записи с операцией в состоянии `sent` ставит в очередь операцию `delete`.

**Why.** Судьба отправленной операции неизвестна устройству ⇒ локальная очистка оставила бы запись на сервере.

### 6. Обязательства тестов

- `T-DM-1` — `delete`(base `v`), затем `update`(base `v`) → `deleted = true`, `body` пуст; краснеет при снятии шага 8.
- `T-DM-2` — `update`(base `v`), затем `delete`(base `v`) → `deleted = true`, `body` пуст; краснеет, если шаг 10 сохраняет `body`.
- `T-DM-3` — повтор одного `op_id` → `version` не изменился; краснеет при снятии шага 2.
- `T-DM-4` — два устройства меняют разные поля от base `v` → оба значения в `body`; краснеет, если шаг 7 отбрасывает всё при `base_version < version`.
- `T-DM-5` — два устройства меняют одно поле от base `v` → второе устройство получает это поле в `rejected_fields`; краснеет, если шаг 6 не читает `field_versions`.
- `T-DM-6` — операция с `base_version = version + 1` → ответ `invalid_base`, `version` не изменился; краснеет при снятии шага 9.
- `T-DM-7` — терминальный ответ сервера → операции нет в очереди, есть строка `ConflictLog`; краснеет, если шаг 11 не пишет `ConflictLog`.

### 7. Решения

- `DM-1`, 2026-08-05, владелец раздела «Синхронизация»: конфликт разрешается по полям на сервере через `field_versions`. Отклонено: last-write-wins по `Operation.created_at` — часы устройства сервер не проверяет, расхождение сверху не ограничено.
- `DM-2`, 2026-08-05, владелец раздела «Синхронизация»: удаление отбрасывает конкурирующую правку. Отклонено: восстановление записи по правке — требует хранить `body` в `tombstone`, объём хранения растёт без верхней границы.
- `DM-3`, 2026-08-05, владелец раздела «Синхронизация»: операции одной записи отправляются последовательно. Отклонено: параллельная отправка — результат зависит от порядка доставки, тесты `T-DM-4` и `T-DM-5` теряют детерминизм.

### 9. Границы раздела

В границах: сущности `Record`, `LocalRecord`, `Operation`, `SyncCursor`, `ConflictLog` и их поля; инварианты INV-1…INV-14; шаги 1–12 разрешения конфликтов; случай удаления против правки.

Вне границ:

- транспорт, кодирование сообщений и политика повторов — раздел «Сетевой слой»;
- аутентификация и проверка `owner_id` — раздел «Безопасность»;
- шифрование локального хранилища — раздел «Безопасность»;
- показ `rejected_fields` пользователю — раздел «Интерфейс», см. `OQ-DM-4`;
- миграции схемы `body` — раздел «Версионирование схемы»;
- сборка мусора по `tombstone` — владелец серверного хранилища, см. `OQ-DM-3`;
- одновременное редактирование одной записи разными `owner_id` — вне продукта, решение владельца продукта;
- прямой обмен между двумя устройствами без сервера — вне продукта, решение владельца продукта.
