## 4. Модель данных и инварианты

### 4.1 Цель

Зафиксировать модель данных синхронизации так, чтобы две реплики одной записи сходились к одному состоянию.

### 4.2 Определения

- **Record** — серверное состояние записи, идентифицируемое `record_id` и версионируемое счётчиком `version`.
- **Tombstone** — версия записи, которая хранит `record_id` и `version` без `payload`.
- **Operation** — элемент клиентской очереди, описывающий одно изменение одной записи.
- **`base_version`** — номер серверной версии, от которой построено изменение в операции.
- **Конфликт** — состояние операции, при котором сервер отклонил часть изменений или всю операцию.

Термины `tombstone`, `idempotency key`, `cursor` используются в значении, принятом в спецификациях репликации и в HTTP Idempotency-Key draft.

### 4.3 Сущности

#### 4.3.1 `Record` — сервер

| Поле | Тип | Правило |
| :--- | :--- | :--- |
| `record_id` | UUID v4 | Назначает клиент при создании |
| `owner_id` | UUID | Идентификатор пользователя-владельца |
| `version` | int64 ≥ 1 | Увеличивает сервер |
| `payload` | JSON object | Отсутствует при `deleted = true` |
| `field_versions` | map<string, int64> | Версия последней записи каждого поля `payload` |
| `deleted` | bool | Признак tombstone |
| `updated_at` | timestamp UTC | Назначает сервер |
| `deleted_at` | timestamp UTC | Заполнено при `deleted = true` |
| `last_op_id` | UUID | `op_id` последней применённой операции |

#### 4.3.2 `LocalRecord` — клиент

| Поле | Тип | Правило |
| :--- | :--- | :--- |
| `record_id` | UUID v4 | Совпадает с серверным |
| `base_version` | int64 ≥ 0 | `0` до первого успешного `create` |
| `server_payload` | JSON object | Последний снимок, полученный от сервера |
| `payload` | JSON object | Снимок с применённой очередью |
| `server_deleted` | bool | Признак tombstone в последнем снимке |
| `pending_op_ids` | list<UUID> | Операции этой записи в порядке очереди |
| `state` | enum | `synced`, `dirty`, `conflict` |

#### 4.3.3 `Operation` — очередь клиента

| Поле | Тип | Правило |
| :--- | :--- | :--- |
| `op_id` | UUID v4 | Ключ идемпотентности, генерирует клиент |
| `seq` | int64 | Монотонный номер в очереди устройства |
| `record_id` | UUID v4 | Целевая запись |
| `device_id` | UUID v4 | Устройство-автор |
| `type` | enum | `create`, `update`, `delete`, `restore` |
| `base_version` | int64 ≥ 0 | Версия снимка на момент создания операции |
| `changed_fields` | map<string, value> | Пусто при `type = delete` |
| `created_at` | timestamp UTC | Часы клиента; в разрешении конфликтов не участвует |
| `state` | enum | `pending`, `sent`, `applied`, `conflict`, `failed` |
| `attempts` | int ≥ 0 | Число отправок |

Переходы `state`: `pending → sent`; `sent → applied`; `sent → pending`; `sent → conflict`; `sent → failed`; `conflict → pending`; `conflict → discarded`.

#### 4.3.4 `Device` — клиент

| Поле | Тип | Правило |
| :--- | :--- | :--- |
| `device_id` | UUID v4 | Сохраняется между перезапусками приложения |
| `owner_id` | UUID | Идентификатор пользователя |
| `sync_cursor` | opaque string | Позиция последней принятой страницы изменений |
| `next_seq` | int64 | Номер для следующей операции очереди |

#### 4.3.5 `ConflictEntry` — клиент

| Поле | Тип | Правило |
| :--- | :--- | :--- |
| `conflict_id` | UUID v4 | Идентификатор записи о конфликте |
| `record_id` | UUID v4 | Целевая запись |
| `op_id` | UUID v4 | Отклонённая операция |
| `server_version` | int64 | Версия записи на момент отклонения |
| `reason` | enum | `stale_fields`, `record_deleted`, `deleted_after_edit` |
| `rejected_values` | map<string, value> | Значения, не попавшие на сервер |
| `resolution` | enum | `pending`, `keep_server`, `resend`, `discarded` |

### 4.4 Инварианты

| ID | Инвариант | Где проверяется |
| :--- | :--- | :--- |
| INV-1 | `record_id` не меняется после создания записи | Сервер отвергает запрос с другим `record_id` |
| INV-2 | `version` строго возрастает во времени | T-1 |
| INV-3 | Применённая операция увеличивает `version` ровно на 1 | T-1 |
| INV-4 | `deleted_at` заполнено тогда и только тогда, когда `deleted = true` | Ограничение схемы БД |
| INV-5 | При `deleted = true` поле `payload` отсутствует | Ограничение схемы БД |
| INV-6 | `field_versions[f] ≤ version` для каждого поля `f` | T-2 |
| INV-7 | `op_id` уникален среди всех операций пользователя | Уникальный индекс журнала операций |
| INV-8 | Повтор `op_id` возвращает результат первого применения | T-4 |
| INV-9 | Очередь устройства отправляет операции в порядке `seq` | T-9 |
| INV-10 | Клиент не отправляет операцию записи до ответа на предыдущую | T-9 |
| INV-11 | `payload` равен `server_payload` с применёнными `pending_op_ids` | T-10 |
| INV-12 | Операция покидает очередь в состоянии `applied` или `discarded` | T-11 |
| INV-13 | Операция в состоянии `conflict` остаётся в очереди до записи `resolution` | T-11 |
| INV-14 | `base_version > 0` для типов `update`, `delete`, `restore` | Валидация запроса на сервере |
| INV-15 | Клиент не записывает `sync_cursor` старее сохранённого | T-8 |
| INV-16 | Очередь переживает перезапуск приложения | T-9 |

### 4.5 Правило разрешения конфликтов

Сервер применяет операцию по следующей процедуре.

1. Прочитать запись по `record_id`. Постусловие: известны `version`, `deleted`, `field_versions`.
2. Проверить `op_id` в журнале применённых операций. Постусловие: при совпадении возвращён прежний ответ, `version` не изменён.
3. При `deleted = true` перейти к §4.6. Постусловие: ветка tombstone выбрана.
4. При `op.base_version = version` применить все поля `changed_fields`. Постусловие: `version` увеличен на 1.
5. При `op.base_version < version` применить поле `f`, если `field_versions[f] ≤ op.base_version`. Постусловие: `field_versions[f]` равен новой `version`.
6. Отклонить поле `f`, если `field_versions[f] > op.base_version`. Постусловие: имя `f` попало в `rejected_fields` ответа.
7. Ответить кодом `200` с полным `payload`, новой `version` и списком `rejected_fields`. Постусловие: клиент имеет серверный снимок.
8. Клиент заменяет `server_payload` ответом и переводит операцию в `applied`. Постусловие: `base_version` равен новой `version`.
9. Клиент создаёт `ConflictEntry` при непустом `rejected_fields`. Постусловие: `LocalRecord.state` равен `conflict`.

Порядок применения операций задаёт порядок их приёма сервером.

**Why.** Часы двух устройств расходятся на величину, которую клиент не ограничивает.

Поле, изменённое обоими устройствами, получает значение операции, принятой сервером позже.

**Why.** `field_versions[f]` растёт только при приёме, поэтому вторая операция видит `field_versions[f] > base_version`.

### 4.6 Удаление против правки

Раздел описывает четыре случая. Устройство A и устройство B правят одну запись версии `N`.

| Случай | Вход | Ответ сервера | Состояние записи | Состояние клиента-автора |
| :--- | :--- | :--- | :--- | :--- |
| C-1 | `delete` от A применён; затем `update` от B с `base_version ≤ N` | `409 record_deleted` | Tombstone, `version` не изменён | `ConflictEntry` с `reason = record_deleted` |
| C-2 | `update` от A применён; затем `delete` от B с `base_version ≤ N` | `200` | Tombstone, `version` увеличен на 1 | Операция в состоянии `applied` |
| C-3 | `delete` от A применён; затем `delete` от B | `200` | Tombstone, `version` не изменён | Операция в состоянии `applied` |
| C-4 | `restore` от B с `base_version` tombstone | `200` | `deleted = false`, `version` увеличен на 1 | Операция в состоянии `applied` |

Правила случаев.

- Сервер применяет `delete` независимо от `base_version` и от значений полей (C-2).

  **Why.** `delete` не читает `payload`, поэтому устаревший снимок не влияет на результат.

- Сервер не применяет `update` и `create` к tombstone (C-1). Клиент сохраняет `changed_fields` в `ConflictEntry.rejected_values`.
- Клиент, получивший tombstone при `LocalRecord.state = dirty`, создаёт `ConflictEntry` с `reason = deleted_after_edit`.
- `restore` создаётся только явным действием пользователя и несёт полный `payload` в `changed_fields`.
- Повторный `delete` не увеличивает `version` (C-3).

  **Why.** Инкремент на каждом повторе сдвигает курсоры всех устройств без изменения состояния.

### 4.7 Решения

- **OD-1**, 2026-08-05, команда sync: конфликт разрешается пополевым слиянием по `field_versions`. Rejected: last-write-wins на уровне записи — теряет изменения непересекающихся полей.
- **OD-2**, 2026-08-05, команда sync: удаление побеждает конкурирующую правку. Rejected: воскрешение записи правкой — удаление становится ненаблюдаемым на устройстве-авторе.
- **OD-3**, 2026-08-05, команда sync: порядок задаёт приём сервером, не `created_at`. Rejected: клиентские часы — сдвиг между устройствами не ограничен сверху.
- **OD-4**, 2026-08-05, команда sync: `op_id` служит ключом идемпотентности. Rejected: дедупликация по хешу тела — две одинаковые правки схлопываются в одну.
- **OD-5**, 2026-08-05, команда sync: версия записи — целочисленный счётчик сервера. Rejected: векторные часы — размер метаданных растёт линейно по числу устройств.

### 4.10 Обязательства тестов

- **T-1** — `update` с `base_version = version` → `version` увеличен на 1; ломается при удалении инкремента.
- **T-2** — два `update` разных полей с одинаковым `base_version` → применены оба поля; ломается при замене слияния на LWW записи.
- **T-3** — два `update` одного поля с одинаковым `base_version` → поле второй операции попало в `rejected_fields`; ломается при снятии сравнения `field_versions`.
- **T-4** — повтор операции с тем же `op_id` → ответ равен первому, `version` не изменён; ломается при отключении журнала `op_id`.
- **T-5** — `update` после применённого `delete` → код `409 record_deleted`; ломается при применении `update` к tombstone.
- **T-6** — `delete` с `base_version < version` → `deleted = true`; ломается при проверке `base_version` для типа `delete`.
- **T-7** — `delete` над tombstone → `version` не изменён; ломается при безусловном инкременте.
- **T-8** — синхронизация с курсором старше срока хранения → код `410 cursor_expired`; ломается при выдаче инкрементальной страницы.
- **T-9** — перезапуск с непустой очередью → порядок `seq` сохранён; ломается при хранении очереди в памяти процесса.
- **T-10** — правка поверх непустой очереди → `payload` равен пересчёту из `server_payload`; ломается при записи правки мимо очереди.
- **T-11** — ответ с непустым `rejected_fields` → операция остаётся в очереди в состоянии `conflict`; ломается при безусловном удалении операции после ответа.
- **T-12** — правка при заполненной очереди → операция отклонена с ошибкой ёмкости; ломается при вытеснении старой операции.
- **T-13** — сдвиг часов назад между двумя правками → `seq` монотонен; ломается при выводе `seq` из `created_at`.
