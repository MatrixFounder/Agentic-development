## 1. Контекст и проблема

### 1.1 Как устроено сейчас

Сессии веб-приложения хранятся в памяти процесса приложения (in-process map: `session_id → session_data`). Идентификатор сессии передаётся клиенту в cookie. Данные сессии не покидают инстанс, на котором сессия была создана.

### 1.2 Следствия

| # | Проблема | Наблюдаемый эффект |
|---|---|---|
| P-01 | Сессии не переживают перезапуск процесса | Каждый деплой, рестарт, OOM-kill или падение пода разлогинивает всех пользователей этого инстанса. Потеря незавершённых пользовательских сценариев (корзина, многошаговые формы). |
| P-02 | Состояние привязано к инстансу | Балансировщик обязан работать в режиме sticky sessions. Это ограничивает алгоритм балансировки, приводит к неравномерной нагрузке и делает вывод инстанса из ротации разрушительным. |
| P-03 | Горизонтальное масштабирование невозможно без деградации | Добавление инстанса не разгружает уже установленные сессии; при autoscale-down сессии на выбывающем инстансе теряются. |
| P-04 | Потребление памяти растёт вместе с числом сессий | Объём сессий влияет на heap приложения, GC-паузы и риск OOM. |
| P-05 | Нет наблюдаемости и управляемости | Нельзя ответить «сколько сейчас активных сессий», нельзя принудительно завершить сессии пользователя, нельзя посмотреть содержимое сессии при разборе инцидента. |

### 1.3 Цель работы

Перенести хранение состояния сессий в Redis так, чтобы:

1. приложение стало stateless по сессиям и допускало произвольную балансировку;
2. деплой и перезапуск инстансов не приводили к разлогиниванию;
3. переход был выполнен без единовременного разлогинивания всех пользователей;
4. поведение при недоступности Redis было явно определено, предсказуемо и не приводило к «зависанию» приложения;
5. политика истечения срока сессии была явной, единой и соответствовала требованиям безопасности.

### 1.4 Допущения

Предметная область описана без привязки к конкретному стеку. Работа специфицируется при следующих допущениях; если какое-либо из них не выполняется, требования подлежат пересмотру на ревью.

- A-01 — приложение уже использует cookie-based session id; формат и способ передачи идентификатора не меняются.
- A-02 — доступ к сессии в коде инкапсулирован (или может быть инкапсулирован малой правкой) за интерфейсом хранилища; прямых обращений к внутренней map вне этого слоя нет либо они устранимы в рамках задачи.
- A-03 — размер типичной сессии — единицы килобайт; в сессии не хранятся большие бинарные объекты.
- A-04 — приложение развёрнуто в одном регионе/датацентре; кросс-региональная репликация сессий не требуется.
- A-05 — доступен управляемый или самостоятельно эксплуатируемый Redis 6.2+ с поддержкой TLS и ACL.

## 2. Область работ

### 2.1 В области работ

- Реализация Redis-бэкенда хранилища сессий за существующим (или новым) интерфейсом `SessionStore`.
- Режим совместимости на время перехода (память + Redis) и управляющий флаг.
- Политика истечения срока: idle-TTL, абсолютный срок жизни, продление.
- Поведение при недоступности Redis: таймауты, circuit breaker, деградация.
- Сериализация, версионирование формата, схема ключей.
- Метрики, логи, алерты, дашборд.
- Нагрузочное тестирование и chaos-проверки.
- Поэтапный раскат и план отката.
- Снятие sticky sessions на балансировщике по завершении перехода.
- Документация: runbook, обновление CLAUDE.md/README раздела о сессиях.

## 3. Требования

Приоритеты: **M** — must (обязательно для приёмки), **S** — should (желательно, допускается перенос при явном согласовании), **C** — could (по возможности).

### 3.1 Функциональные требования — хранилище

| ID | Приоритет | Требование |
|---|---|---|
| FR-01 | M | Состояние сессии сохраняется в Redis и доступно любому инстансу приложения без привязки к тому, где сессия была создана. |
| FR-02 | M | Реализуются операции: `create`, `read`, `update`, `delete`, `touch` (продление TTL), `regenerate_id` (смена идентификатора с переносом данных). |
| FR-03 | M | Ключ формируется по схеме `sess:v1:{session_id}`. Префикс `sess` и версия схемы конфигурируемы. Идентификатор сессии не логируется в открытом виде (см. SEC-04). |
| FR-04 | M | Значение — сериализованный документ с полями: `v` (версия формата), `sid_hash`, `uid`, `created_at`, `last_seen_at`, `abs_exp` (абсолютный срок), `data` (пользовательский payload), `attrs` (служебные атрибуты: ip-подсеть, user-agent-хэш). |
| FR-05 | M | Формат сериализации — JSON (UTF-8). Читатель обязан игнорировать неизвестные поля и сохранять их при обратной записи (forward compatibility). |
| FR-06 | M | Смена мажорной версии формата (`v`) не ломает работающие инстансы: читатель поддерживает как минимум текущую и предыдущую версию. |
| FR-07 | M | Одно обращение к приложению за сессией порождает не более одного round-trip на чтение. Запись выполняется только если сессия помечена «грязной» либо требуется продление TTL (см. FR-11). |
| FR-08 | M | Размер сериализованной сессии ограничен `session.max_payload_bytes` (по умолчанию 8 КиБ). Попытка превысить лимит завершается ошибкой уровня приложения, инкрементом метрики и записью в лог; молчаливое усечение запрещено. |
| FR-09 | M | Удаление сессии (logout) немедленно удаляет ключ из Redis. |
| FR-10 | S | Поддерживается индекс сессий пользователя `usess:v1:{uid}` (Redis SET) для перечисления и массового завершения сессий. Индекс самоочищается: при чтении отсутствующие элементы удаляются из множества; на само множество ставится TTL не меньше `session.absolute_ttl`. |

### 3.2 Функциональные требования — политика истечения срока

| ID | Приоритет | Требование |
|---|---|---|
| FR-11 | M | Действует **скользящий idle-TTL**: `session.idle_ttl` (по умолчанию 30 минут), реализуемый через `EXPIRE`/`SET ... EX` на ключе Redis. TTL — единственный источник истины по бездействию; отдельного фонового сборщика мусора нет. |
| FR-12 | M | Продление TTL выполняется не чаще, чем раз в `session.touch_interval` (по умолчанию 60 секунд) на сессию, чтобы не порождать запись на каждый HTTP-запрос. Точность момента истечения — в пределах `touch_interval`. |
| FR-13 | M | Действует **абсолютный срок жизни** `session.absolute_ttl` (по умолчанию 12 часов) от момента создания сессии. Он хранится в поле `abs_exp` и проверяется приложением при каждом чтении: сессия с истёкшим `abs_exp` считается недействительной, её ключ удаляется, пользователь перенаправляется на логин. |
| FR-14 | M | Redis-TTL ключа устанавливается как `min(idle_ttl, abs_exp − now)`, чтобы ключ не переживал абсолютный срок. |
| FR-15 | M | При успешной аутентификации и при любом повышении привилегий идентификатор сессии перевыпускается (`regenerate_id`): создаётся новый ключ, старый удаляется атомарно с точки зрения приложения. Счётчик абсолютного срока при аутентификации сбрасывается. |
| FR-16 | S | Значения `idle_ttl`, `absolute_ttl`, `touch_interval` задаются конфигурацией без пересборки и применяются к вновь создаваемым и продлеваемым сессиям без рестарта (при поддержке hot-reload конфигурации). |
| FR-17 | C | Поддерживается пер-роль переопределение `idle_ttl` (например, более короткий срок для административных ролей). |

### 3.3 Функциональные требования — поведение при недоступности Redis

Под недоступностью понимаются: отказ соединения, превышение таймаута, ошибка репликации/failover, ответ `LOADING`, `READONLY`, `OOM`.

| ID | Приоритет | Требование |
|---|---|---|
| FR-18 | M | Все обращения к Redis ограничены таймаутами: `connect_timeout` 150 мс, `command_timeout` 100 мс (конфигурируемо). Ни один пользовательский запрос не блокируется на хранилище сессий дольше `command_timeout` × (1 + число ретраев). |
| FR-19 | M | Ретрай допускается только для идемпотентных операций чтения и не более одного раза. Операции записи не ретраятся автоматически. |
| FR-20 | M | Реализуется circuit breaker: при доле ошибок ≥ 50 % на окне 10 с и не менее 20 запросов размыкатель переходит в open на 5 с, затем в half-open (пробные запросы). В состоянии open обращения к Redis не выполняются — ошибка возвращается немедленно. |
| FR-21 | M | При недоступности Redis **сессия не считается уничтоженной**: ключ не удаляется, запрос не приводит к принудительному logout и очистке cookie. |
| FR-22 | M | Fallback на in-memory хранилище при недоступности Redis запрещён (см. D-04). |
| FR-23 | M | Поведение при недоступности зависит от типа запроса:<br>• **безопасные методы** (GET/HEAD/OPTIONS) — обслуживаются из локального read-through кэша, если снимок сессии в нём есть и его возраст ≤ `session.stale_grace` (по умолчанию 60 с); иначе запрос обрабатывается как анонимный либо получает 503 согласно FR-24;<br>• **изменяющие методы** и любые операции, требующие записи в сессию, — отвечают `503 Service Unavailable` с заголовком `Retry-After: 5`. Изменения сессии при этом не считаются сохранёнными. |
| FR-24 | M | Для маршрутов, помеченных как публичные/анонимные, недоступность Redis не должна приводить к ошибке: запрос обслуживается как анонимный. Для маршрутов, требующих аутентификации, возвращается 503, а не редирект на логин (чтобы не разлогинивать пользователя из-за инфраструктурного сбоя). |
| FR-25 | M | Локальный кэш сессий: только положительные снимки, TTL `session.local_cache_ttl` (по умолчанию 5 с), ограничение по размеру, вытеснение LRU. Кэш инвалидируется локально при `update`/`delete`/`regenerate_id`. |
| FR-26 | M | Каждый переход состояния размыкателя и каждый период деградации фиксируются в логе (уровень WARN/ERROR) и в метриках. |
| FR-27 | S | Наличие и параметры локального кэша конфигурируемы, включая полное отключение (`session.local_cache_ttl = 0`). |

### 3.4 Требования совместимости и миграции

| ID | Приоритет | Требование |
|---|---|---|
| MIG-01 | M | Вводится конфигурационный флаг `session.store` со значениями: `memory` (текущее поведение), `dual` (переходный режим), `redis` (целевое). Значение по умолчанию на момент выкладки кода — `memory`. |
| MIG-02 | M | В режиме `dual` чтение выполняется сначала из Redis; при промахе — из памяти процесса. Если сессия найдена в памяти, она **прозрачно переносится** в Redis (write-through) и далее живёт там. |
| MIG-03 | M | В режиме `dual` запись выполняется в Redis; в память пишется только для сессий, ещё не мигрированных, чтобы обеспечить откат. Ошибка записи в Redis в режиме `dual` не приводит к отказу запроса — фиксируется метрика и лог. |
| MIG-04 | M | Формат session id и cookie при переходе не меняется: существующие cookie остаются валидными. |
| MIG-05 | M | Sticky sessions на балансировщике сохраняются на всё время фаз 0–2 (см. §6) и снимаются отдельным шагом только после подтверждения работы в режиме `redis`. |
| MIG-06 | M | Откат с `redis` на `dual`/`memory` возможен изменением конфигурации и перезапуском инстансов, без обратной миграции данных. Допускается разлогинивание пользователей при откате — это должно быть явно указано в runbook. |
| MIG-07 | M | Переключение режима не требует изменения кода вызывающих мест: интерфейс `SessionStore` остаётся единственной точкой доступа. |
| MIG-08 | S | По завершении перехода in-memory реализация и флаг `dual` удаляются из кода отдельным PR (техдолг с указанным сроком). |

### 3.6 Требования безопасности

| ID | Приоритет | Требование |
|---|---|---|
| SEC-01 | M | Соединение с Redis — только по TLS. Аутентификация — Redis ACL-пользователь с паролем из секрет-хранилища; пароль не хранится в репозитории и не попадает в логи. |
| SEC-02 | M | ACL-пользователь приложения ограничен: доступ только к ключам `sess:*` и `usess:*`, разрешённые команды — минимально необходимый набор (`GET`, `SET`, `DEL`, `EXPIRE`, `TTL`, `SADD`, `SREM`, `SMEMBERS`, `EXISTS`, `UNLINK`). Административные команды (`FLUSHDB`, `FLUSHALL`, `CONFIG`, `KEYS`, `SHUTDOWN`) запрещены. |
| SEC-03 | M | Идентификатор сессии — не менее 128 бит энтропии из CSPRNG. |
| SEC-04 | M | Session id не пишется в логи, трассировки и метрики. Для корреляции используется усечённый хэш (`sid_hash` = первые 16 hex-символов SHA-256 от sid). |
| SEC-05 | M | Cookie сессии: `HttpOnly`, `Secure`, `SameSite=Lax` (или `Strict`, если это не ломает сценарии), `Path=/`, без `Domain` шире необходимого. |
| SEC-06 | M | В payload сессии не хранятся: пароли, полные номера карт, персональные данные сверх минимально необходимого. Хранятся идентификатор пользователя, роли/права, служебные атрибуты. |
| SEC-07 | M | Redis-инстанс сессий изолирован сетевым доступом: подключение разрешено только с адресов приложения. |
| SEC-08 | S | Реализована проверка привязки сессии к клиенту (совпадение подсети /24 и хэша user-agent) с режимом «логировать» по умолчанию и возможностью включить «отклонять». |
| SEC-09 | S | Массовое завершение сессий пользователя доступно как административная операция и фиксируется в audit log. |

### 3.7 Эксплуатационные требования

| ID | Приоритет | Требование |
|---|---|---|
| OPS-01 | M | Для сессий выделяется отдельный Redis-инстанс либо отдельная логическая БД, не разделяемая с кэшами приложения. |
| OPS-02 | M | `maxmemory-policy` = `noeviction`. Вытеснение живых сессий по LRU запрещено — при исчерпании памяти система должна отказывать явно, а не молча разлогинивать пользователей (см. D-07). |
| OPS-03 | M | Персистентность: AOF `appendfsync everysec`. Допустима потеря не более 1 секунды записей при отказе узла. |
| OPS-04 | M | Топология с репликой и автоматическим failover (Sentinel / managed-решение) — см. OQ-01. |
| OPS-05 | M | Экспортируются метрики: `session_store_ops_total{op,result}`, `session_store_op_duration_seconds{op}`, `session_store_cache_hits_total{result}`, `session_store_breaker_state`, `session_store_payload_bytes` (гистограмма), `session_active_estimate`, `session_expired_total{reason=idle|absolute|logout}`. |
| OPS-06 | M | Алерты: доступность Redis; доля ошибок хранилища > 1 % за 5 мин; p99 операции > 20 мс за 5 мин; `used_memory` > 70 % `maxmemory`; размыкатель в состоянии open дольше 60 с; отсутствие реплики. |
| OPS-07 | M | Дашборд с ключевыми метриками создан и приложен к задаче ссылкой. |
| OPS-08 | M | Runbook описывает: отказ Redis, исчерпание памяти, failover, откат на `dual`/`memory`, массовое завершение сессий, диагностику «пользователя разлогинивает». |
| OPS-09 | S | Оценка потребления памяти Redis: `средний размер сессии × пиковое число сессий × коэффициент накладных расходов (1.5)`; результат зафиксирован в задаче и заложен в sizing. |

## 4. Сценарии использования

Формат: предусловие → шаги → ожидаемый результат.

### UC-01. Создание сессии при входе

**Предусловие:** пользователь не аутентифицирован, `session.store = redis`.
1. Пользователь отправляет корректные учётные данные.
2. Приложение генерирует новый session id (SEC-03), формирует документ сессии, устанавливает `created_at`, `abs_exp = now + absolute_ttl`.
3. Выполняется `SET sess:v1:{sid} <json> EX min(idle_ttl, abs_exp − now) NX`.
4. При включённом FR-10 — `SADD usess:v1:{uid} {sid}`.
5. Клиенту устанавливается cookie.

**Результат:** сессия доступна с любого инстанса; предыдущий анонимный session id (если был) удалён (FR-15).

### UC-02. Обработка запроса с существующей сессией

**Предусловие:** валидная cookie, Redis доступен.
1. Инстанс читает `GET sess:v1:{sid}` (или берёт снимок из локального кэша в пределах `local_cache_ttl`).
2. Проверяется `abs_exp`; при истечении — переход к UC-06.
3. Запрос обрабатывается.
4. Если сессия изменена — запись; иначе, если с момента `last_seen_at` прошло ≥ `touch_interval`, — продление TTL.

**Результат:** ≤ 1 round-trip на чтение (FR-07); запись не на каждый запрос (FR-12).

### UC-03. Запрос, попавший на другой инстанс

**Предусловие:** sticky sessions отключены (фаза 3).
1. Балансировщик направляет запрос на инстанс, который эту сессию не создавал.
2. Инстанс читает сессию из Redis.

**Результат:** запрос обслуживается идентично UC-02; пользователь не замечает смену инстанса.

### UC-04. Деплой / перезапуск / autoscale

**Предусловие:** режим `redis`, идёт rolling update.
1. Инстансы поочерёдно останавливаются и поднимаются.
2. Запросы перебалансируются на живые инстансы.

**Результат:** ни одна активная сессия не потеряна; число принудительных логинов, вызванных деплоем, равно нулю.

### UC-05. Выход пользователя

1. Пользователь нажимает «Выйти».
2. Приложение выполняет `UNLINK sess:v1:{sid}`, `SREM usess:v1:{uid} {sid}`, чистит локальный кэш инстанса, инвалидирует cookie.

**Результат:** сессия недействительна. Допустимая аномалия: на других инстансах снимок в локальном кэше может жить до `local_cache_ttl` (см. R-03).

### UC-06. Истечение срока

**Вариант A (бездействие):** ключ удалён Redis по TTL → чтение возвращает промах → пользователь считается анонимным, перенаправляется на логин, метрика `session_expired_total{reason="idle"}`.
**Вариант B (абсолютный срок):** ключ существует, но `abs_exp ≤ now` → приложение удаляет ключ, считает сессию недействительной, метрика `reason="absolute"`.

### UC-07. Redis недоступен, безопасный запрос

**Предусловие:** размыкатель open.
1. Пользователь открывает страницу (GET), требующую аутентификации.
2. Есть снимок в локальном кэше возрастом ≤ `stale_grace` → страница отдаётся с данными из снимка (возможно устаревшими).
3. Снимка нет → ответ 503 с `Retry-After` (для аутентифицированного маршрута) либо анонимная обработка (для публичного).

**Результат:** cookie не сбрасывается; после восстановления Redis работа продолжается без повторного логина.

### UC-08. Redis недоступен, изменяющий запрос

1. Пользователь отправляет форму (POST).
2. Хранилище недоступно → 503 + `Retry-After: 5`; изменения в сессии не считаются применёнными; побочные эффекты, зависящие от сессии, не выполняются.

**Результат:** явный отказ вместо молчаливой потери состояния.

### UC-09. Failover Redis

1. Мастер выходит из строя, реплика повышается.
2. Клиент приложения обнаруживает разрыв, размыкатель размыкается, часть запросов получает 503.
3. После завершения failover соединения переустанавливаются, размыкатель закрывается.

**Результат:** восстановление ≤ 30 с (NFR-06), сессии сохранены с точностью до окна `appendfsync everysec`.

### UC-10. Переходный период, сессия создана до миграции

**Предусловие:** режим `dual`, sticky sessions включены.
1. Запрос со «старой» cookie попадает на инстанс, где сессия лежит в памяти.
2. Чтение из Redis — промах; чтение из памяти — попадание.
3. Сессия записывается в Redis (MIG-02).
4. Последующие запросы обслуживаются из Redis, в том числе с других инстансов.

**Результат:** переход без разлогинивания пользователей.

### UC-11. Массовое завершение сессий пользователя (FR-10, SEC-09)

1. Администратор (или сам пользователь через «Выйти на всех устройствах») инициирует операцию.
2. Читается `SMEMBERS usess:v1:{uid}`, выполняется `UNLINK` по каждому ключу, множество очищается.
3. Событие пишется в audit log.

**Результат:** все сессии пользователя недействительны в пределах `local_cache_ttl`.

### UC-12. Превышение лимита размера сессии

1. Код пытается положить в сессию объект, после сериализации превышающий `max_payload_bytes`.
2. Операция завершается ошибкой уровня приложения, инкрементируется метрика, пишется лог с `sid_hash` и размером.

**Результат:** переполнение не остаётся незамеченным; данные не теряются молча.

### UC-13. Разбор инцидента

1. Дежурный по `sid_hash` из логов находит ключ и смотрит TTL и содержимое сессии через административный доступ.

**Результат:** возможен ответ на вопрос «почему пользователя разлогинило».

## 5. Критерии приёмки

Формат Given/When/Then. Все критерии проверяются автоматизированно, кроме явно помеченных как ручные.

| ID | Требования | Критерий |
|---|---|---|
| AC-01 | FR-01, UC-03 | **Given** запущены 3 инстанса за балансировщиком без sticky, **when** выполняется 100 последовательных запросов с одной cookie, распределённых по всем инстансам, **then** все 100 обслужены как аутентифицированные, состояние сессии консистентно. |
| AC-02 | FR-01, UC-04 | **Given** активны N сессий, **when** выполняется rolling restart всех инстансов, **then** после рестарта 100 % сессий валидны, число редиректов на логин — 0. |
| AC-03 | FR-11, FR-12 | **Given** `idle_ttl = 60s`, `touch_interval = 10s`, **when** запросы идут раз в 5 с, **then** сессия жива неограниченно долго, а число операций записи ≤ 1 на каждые 10 с; **when** запросы прекращаются, **then** сессия становится недействительной через 60–70 с. |
| AC-04 | FR-13, FR-14 | **Given** `absolute_ttl = 2m` при активном использовании, **when** проходит 2 минуты, **then** сессия признаётся недействительной с `reason="absolute"`, ключ удалён, TTL ключа никогда не превышал остаток абсолютного срока. |

## 6. План перехода

| Фаза | Конфигурация | Что делаем | Критерий перехода к следующей фазе |
|---|---|---|---|
| 0. Подготовка | `memory` | Redis развёрнут, ACL/TLS настроены, метрики и дашборд готовы, код выложен с флагом по умолчанию `memory`. | Дашборд работает, синтетический тест записи/чтения в Redis зелёный. |
| 1. Теневой прогон | `dual`, sticky **включены** | Включаем на 1 инстансе (или 5 % трафика). Наблюдаем задержки, ошибки, размеры payload. | 24 часа без роста ошибок и деградации задержек; AC-10 выполнен. |
| 2. Полный `dual` | `dual`, sticky **включены** | Раскатываем на 100 % инстансов; активные сессии мигрируют лениво. | ≥ 95 % активных сессий обслуживаются из Redis; доля попаданий в память < 5 %. |
| 3. Целевой режим | `redis`, sticky **включены** | Отключаем чтение из памяти. Наблюдаем 48 часов. | Отсутствие всплеска логинов; ошибки хранилища < 0.1 %. |
| 4. Снятие sticky | `redis`, sticky **выключены** | Меняем конфигурацию балансировщика на round-robin / least-conn. | AC-23 выполнен. |
| 5. Уборка | `redis` | Удаляем in-memory реализацию, режим `dual` и связанный код (MIG-08). | Код смержен, документация обновлена. |

**Откат:** на фазах 1–3 — возврат конфигурации на предыдущее значение (см. MIG-06). На фазе 4 — возврат sticky sessions на балансировщике (мгновенный, без деплоя). После фазы 5 откат не предусмотрен.

## 7. Принятые решения

| ID | Решение | Обоснование | Отвергнутая альтернатива |
|---|---|---|---|
| D-01 | Серверные сессии сохраняются; переход на stateless-токены не выполняется. | Позволяет мгновенно отзывать сессии и не переписывать модель авторизации. Задача — снять привязку к инстансу, а не сменить парадигму. | JWT в cookie — отзывать сложно, требует списка отзыва, что возвращает нас к общему хранилищу. |
| D-02 | Хранилище — Redis. | Уже эксплуатируется в компании, есть экспертиза, подходящая модель TTL из коробки. | БД приложения — лишняя нагрузка на OLTP, ручная очистка просроченных строк; Memcached — нет персистентности и репликации. |
| D-03 | Скользящий idle-TTL 30 мин + жёсткий абсолютный срок 12 ч. | Idle-TTL держит UX, абсолютный срок ограничивает окно эксплуатации украденной cookie. | Только абсолютный TTL — либо разлогинивает активных пользователей, либо слишком длинное окно риска. |
| D-04 | При недоступности Redis — **fail-closed**, без отката в память процесса. | Откат в память возвращает P-02 (расхождение состояния между инстансами) и создаёт split-brain: одна и та же сессия существует в двух версиях. Явный 503 честнее молчаливой потери данных. | Fallback в память — отвергнут; «разлогинивать пользователя» — отвергнут, так как инфраструктурный сбой не должен уничтожать пользовательский вход. |
| D-05 | Кратковременный локальный read-through кэш (5 с) + `stale_grace` 60 с для безопасных методов. | Гасит короткие сетевые всплески и failover, снижает нагрузку на Redis, без него p99 приложения полностью определяется p99 Redis. | Отсутствие кэша — хуже переживает моргания сети; длинный кэш — задерживает распространение logout. Компромисс зафиксирован в R-03. |
| D-06 | Продление TTL не чаще раза в 60 с. | Иначе каждый HTTP-запрос порождает запись; на целевом RPS это удваивает нагрузку на Redis без пользы. | Продление на каждом запросе — отвергнуто по стоимости. |
| D-07 | `maxmemory-policy = noeviction` на инстансе сессий. | При `allkeys-lru`/`volatile-lru` переполнение памяти выражается в случайном разлогинивании пользователей без единого сигнала в логах приложения. Явный отказ записи диагностируется мгновенно. | LRU-вытеснение — отвергнуто. |
| D-08 | Формат — JSON, поле версии `v`, читатели терпимы к неизвестным полям. | Читаемость при разборе инцидентов важнее нескольких процентов размера; версионирование позволяет менять схему без единовременного деплоя. | MessagePack/protobuf — компактнее, но требует инструментов для отладки; возврат к вопросу при подтверждённой проблеме с объёмом. |
| D-09 | Содержимое сессии не шифруется приложением; защита — TLS в транспорте, сетевая изоляция и ACL, плюс запрет на хранение чувствительных данных (SEC-06). | Шифрование payload не защищает от компрометации приложения (у него есть ключ) и усложняет отладку. | Шифрование на уровне приложения — отложено; вернуться, если в сессии появятся регулируемые данные (OQ-04). |
| D-10 | Конкурентные записи в одну сессию разрешаются по принципу «последняя запись побеждает» на уровне всего документа. | Типовой профиль — редкие записи в сессию; оптимистичные блокировки (`WATCH`/`MULTI`) усложняют код ради редкого класса гонок. | Оптимистичная блокировка и пофайловый merge — отложены; см. R-02 и OQ-07. |
| D-11 | Sticky sessions снимаются отдельным шагом после подтверждения работы в режиме `redis`, а не одновременно с переключением. | Разделение изменений позволяет откатить каждое по отдельности и однозначно атрибутировать регрессию. | Одновременное переключение — отвергнуто как рискованное. |
| D-12 | Отдельный Redis-инстанс (или отдельная логическая БД) для сессий. | Изоляция от кэшей: чужой всплеск не вытесняет сессии, разные политики памяти и персистентности. | Общий инстанс с кэшами — отвергнут. |
